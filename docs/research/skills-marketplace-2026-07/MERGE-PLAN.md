# 功能广场 × Skills 市场 · 融合设计方案

> 目标:把「Skills 市场」并入「功能广场」的路由/页面,形成一个统一的「科研能力发现入口」。
> 核心难点:两者**性质不同** —— 功能广场是**静态、公开、admin 策展的全网工具黄页**;Skills 是**动态、用户上传、需审核、可装进 agent 的社区技能**。硬合并会互相拖累,需重新做信息架构。

---

## 1. 现状对比(为什么不能简单合并)

| 维度 | 功能广场(feature_tools) | Skills 市场(user_skills) |
|---|---|---|
| **本质** | 全网学术工具「黄页」——外部网站/软件的介绍 | 用户上传的 **Agent Skill**(SKILL.md bundle),装进 AI 用 |
| **来源** | **admin 批量导入 + webhook 同步**(只读策展) | **用户上传 + 审核**(UGC) |
| **公开性** | **完全公开免登录**(`/public/tools*` + SEO sitemap) | 列表**登录才可见**(`/user/skills/market`);仅详情/下载公开 |
| **主动作** | 访问官网 / 获取下载(**外链出去**) | 安装到智能助手 / 去使用(**装进 agent** curl 一行) |
| **数据模型** | 富黄页(logo/价格/官网/FAQ/评测/12 学术分类/vendor…) | 精简(作者/安装量/版本/文件清单/frontmatter) |
| **分类** | 固定 12 个学术领域 | 自由 category(research/writing…) |
| **详情页** | ToolDetailPage(访问/下载/收藏) | SkillDetailPage(安装/去使用/分享/举报) |
| **卡片** | ToolCard(logo + 官网 + 价格) | SkillCard(作者 + 安装量) |

**结论**:两者是「发现科研能力」的一体两面,但**实体性质、贡献模型、主动作、公开性都不同**。合并应发生在**信息架构 / 页面外壳层**,而**不是数据层**(两个后端模块保持独立)。

> 关键洞察:功能广场**移动首页已经有「站内功能 vs 全网功能」两大支柱**(`MobileToolsHomePage`)。Skills 恰好是天然的**第三支柱**——既不是"外部工具",也不是"我们平台的功能",而是"**社区贡献的、装进 AI 的技能**"。

---

## 2. 推荐方案:「功能广场」升级为三支柱能力中心 + 共享外壳 + 分段切换

### 2.1 定位升级
功能广场从「全网工具黄页」升级为 **「科研能力广场」**:一站发现三类能力 ——
1. **站内功能**(Scholay 原生:智能助手 / 写作 / 审稿 / 文献集)—— 导览入口(已有 MENUS 数据)
2. **全网工具**(feature_tools 黄页,访问官网 / 下载)—— 现状不变
3. **社区技能**(user_skills,用户上传、装进 claw / 外部 agent)—— **新增,复用功能广场外壳**

### 2.2 为什么不选另外两种做法
- **❌ 混排统一 feed**(工具和技能混在一个列表,用 badge 区分):两者卡片信息密度差异大(工具有官网/价格,技能有作者/安装量)、详情动作完全不同、筛选维度不同 → 混排会让两边都"半残",且难做 SEO/筛选。
- **❌ 完全独立两个页面**(只是导航并列):没达成用户"复用功能广场页面"的诉求,也丢了"一站发现"的价值。
- **✅ 共享外壳 + 分段(Tab)切换**:功能广场的 `ToolsLayout`(侧栏 + `<Outlet/>`)外壳复用,顶部加分段「全网工具 | 社区技能」,**各自保留自己的数据源、筛选器、卡片、详情动作**。既复用页面框架、统一入口,又不牺牲各自的信息完整度。这是黄页站(如 Product Hunt / 各类 marketplace)成熟做法。

## 3. 信息架构与导航

### 3.1 桌面(功能广场壳内分段)
```
/tools  (ToolsLayout 外壳:SidebarLayout + Outlet,不重挂)
├── 顶部分段:  [ 全网工具 ]  [ 社区技能 ]        ← 新增 Segmented control
├── 侧栏 ToolsSidebar:
│     · 全网工具 tab → 现有筛选(分类12类 / 价格 / 形式 / 开源)
│     · 社区技能 tab → 技能筛选(分类 / 排序 热门·最新 / 来源)+「+ 上传技能」CTA
└── 主区 <Outlet/>:
      · /tools           全网工具目录(ToolsCatalogPage,现状)
      · /tools/skills     社区技能目录(SkillsMarketPage 复用进壳)
      · /tools/:slug      工具详情(ToolDetailPage,现状)
      · /tools/skills/:slug 技能详情(SkillDetailPage 复用进壳)
      · /tools/skills/new  上传技能(SkillCreatePage)
```

### 3.2 移动端(首页第三块)
`MobileToolsHomePage` 现有「站内功能 / 全网功能」两块,**加第三块「社区技能」**:横幅 + 精选技能卡 → `/m/tools/skills` 列表。移动技能详情复用 `/m/tools/skills/:slug`。

### 3.3 主菜单(menus.ts)
- 保留「功能广场」条目(可改副标题为「工具 · 技能」)。
- 上一轮我加的「技能市场」独立条目 → **改为指向功能广场的技能分段** `/tools/skills`(或直接移除独立条目,统一到功能广场),避免两个入口指向割裂的页面。
- 顶栏功能菜单浮层里,功能广场描述更新为「全网工具 + 社区技能」。

## 4. 路由方案(含兼容)

| 路径 | 内容 | 处置 |
|---|---|---|
| `/tools` | 全网工具目录(默认段) | 不变 |
| `/tools/:slug` | 工具详情 | 不变(注意:`skills` 是保留段,不会撞) |
| `/tools/skills` | 社区技能目录 | **新增**(静态段,排在 `:slug` 之前) |
| `/tools/skills/new` | 上传技能向导 | 新增(= 迁 `/skills/new`) |
| `/tools/skills/:slug` | 技能详情 / 分享落地页 | 新增(= 迁 `/skills/:idOrSlug`) |
| `/skills*`(旧) | 我上一轮建的独立路由 | **301 → `/tools/skills*`**,或保留 `/skills/:slug` 作**对外分享短链 alias**(更短更好记,跨 agent 场景推荐保留短链) |
| `/skills/mine` | 我的技能 | → `/tools/skills/mine` |

**slug 命名空间**:`feature_tools.slug` 与 `user_skills.slug` 是**两个独立空间**,靠路径前缀 `/tools/:slug` vs `/tools/skills/:slug` 区分,不冲突。分享短链建议保留 `/skills/<slug>`(对外 install 命令里的 URL 更干净)。

---

## 5. 数据层(关键补齐:公开技能列表端点)

**两个后端模块不合并。** 前端功能广场壳按当前分段调不同 public API。

**必须补齐**:功能广场是**完全公开免登录**的(SEO),而 Skills 列表现在**登录才可见**。要让"社区技能"融入公开黄页,需新增:
- `GET /api/v1/public/skills`(免登录列 **public + approved + active** 技能,支持 q/category/sort/page)—— 复用现有 `repo.ListMarket`/`ListApprovedPublic`,去掉 auth。
- `GET /api/v1/public/skills/categories`(公开技能分类聚合)。
- 前端 `usePublicSkillMarket`(匿名)与现有 `useSkillMarket`(登录,带 installed 标记)分流:匿名走 public 端点(无 installed 状态),登录走带态端点。
- **SEO**:公开 approved 技能进 sitemap(新增 `sitemap-skills.xml` 或并入,仿 `featuretool/sitemap.go`)。

> 收益:社区技能页也能被搜索引擎收录 + 匿名分享落地,和全网工具一致。

---

## 6. 差异处理(筛选 / 卡片 / 详情)

- **侧栏筛选**:`ToolsSidebar` 按当前分段渲染不同筛选组 —— 工具段用现有(分类/价格/形式/开源);技能段用(分类 / 排序 / 来源 self·market)。二者共用「搜索框 + 清空 + chip」骨架。
- **卡片**:各用各的(`ToolCard` / `SkillGridCard`),分段决定渲染哪种。不强行统一样式。
- **详情动作**:工具 = 访问官网 / 获取下载;技能 = 安装到智能助手 / 去使用(curl)/ 分享 / 举报。各自详情页复用进壳即可,动作区天然不同。
- **收藏 / 统计**:工具有 view/favorite;技能有 install_count。展示各自的即可。

---

## 7. 贡献模型的融合(功能广场"半 UGC 化")

这是**产品定位的实质变化**,需在方案里点明:
- 功能广场原本是**只读黄页**(admin 导入)。合并后,「社区技能」分段是 **UGC**(用户上传 + 审核)。
- 所以功能广场页面要出现「**+ 上传技能**」入口(仅在技能分段,→ `/tools/skills/new`),以及「我的技能」管理入口。
- 全网工具**仍只 admin 导入**(不开放用户提交工具——那是另一个更大的话题)。
- 一句话:**功能广场 = admin 策展的全网工具 + 用户共创的社区技能**,两种贡献模型并存、分段隔离。

---

## 8. admin / SEO / 命名

- **admin**:保留两套后台(工具导入/webhook + 技能审核队列),后台导航「内容运营」组并列即可,无需合并。
- **SEO**:新增技能 sitemap(见 §5)。
- **命名建议**(需拍板,给三个选项):
  1. 保留「功能广场」,副标题「全网工具 · 社区技能」(改动最小)
  2. 「科研能力广场」/「能力广场」(涵盖工具+技能+站内)
  3. 「工具 & 技能」(直白)
  英文 `Playground` 三者都涵盖,可不变。

---

## 9. 分期落地

**Phase 1(核心融合,能上线的最小闭环)**
- 后端:新增 `/public/skills` + `/public/skills/categories`(免登录列 approved public)。
- 前端:`ToolsLayout` 顶部加分段;`ToolsSidebar` 按段切筛选;技能目录/详情/上传**复用进 `/tools/skills*`**;匿名走 public 端点。
- `menus.ts`:功能广场描述更新;「技能市场」独立条目改指 `/tools/skills`(或移除)。
- 旧 `/skills*` → 301 到 `/tools/skills*`;保留 `/skills/<slug>` 分享短链 alias。

**Phase 2(增强)**
- 移动首页第三块「社区技能」+ 移动技能列表/详情。
- 桌面功能广场首页加「站内功能」导览块(读 MENUS)。
- 技能 SEO sitemap;统一搜索(一个搜索框跨工具+技能,可选)。

**Phase 3(可选,远期)**
- 「站内功能 / 全网工具 / 社区技能」三支柱统一 landing(桌面也学移动首页的分块首页)。
- 混合推荐 feed(首页精选跨三类)。

---

## 10. 需 owner 拍板的决策点

1. **命名**:功能广场保留 + 副标题,还是改名(§8)?
2. **`/skills` 旧路由**:全量 301 到 `/tools/skills`,还是保留 `/skills/<slug>` 作对外分享短链(推荐保留短链——跨 agent install URL 更干净)?
3. **主菜单**:「技能市场」独立入口移除并入功能广场,还是两个入口都留(功能广场 = 综合,技能市场 = 直达技能段)?
4. **公开浏览**:确认「社区技能」列表要**免登录 + 进 SEO**(与全网工具一致)——这是让它真正融入功能广场的前提。
5. **站内功能块**是否本期做(Phase 1 vs Phase 2)。
6. 是否开放**用户提交全网工具**(本方案默认**不开**,工具仍 admin 策展)。

---

**一句话**:不改数据层、不硬混排;把功能广场升级成「工具 + 技能」的**分段式能力中心**,复用其外壳/侧栏/SEO/移动首页框架,补一个**公开技能列表端点**让社区技能像全网工具一样可匿名浏览与被收录,并让功能广场从「只读黄页」正式接纳「用户共创」这一支柱。
