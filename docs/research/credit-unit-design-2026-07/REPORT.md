# 充值币 / 点数单位设计 —— 同类产品调研 2026-07

> 起因:当前设计是**两层换算**(¥1 = 60 经费 → 1 经费 = 5 算力点 ⇒ ¥1 = 300 算力点),
> 两个 admin 旋钮控制一个结果。本文调查同类产品实际怎么做。
>
> 方法:5 路并行检索 + 逐条**回访来源**对抗验证(36 agents)。
> **16 条核实 / 14 条被推翻** —— 推翻率之高本身是结论的一部分:这个题目上「看起来像」的说法
> 大多经不起回访(最常见的错是把「credits」当成第二层币,而它在多数产品里**就是美元**)。
>
> ⚠️ 所有事实附来源 URL;拿不到来源的一律标注未核实,不写进结论。法规部分见文末保留意见。

## 一、业界全景

1. 【类型一 · 一层，且单位就是钱】开发者 API / 云厂商的压倒性主流：充值余额直接以法币计价，消费按上游 token 单价实扣，中间没有任何命名单位。OpenAI Platform（最低 $5、默认 $10、购买后 1 年过期不退、auto-recharge 现已默认开启、零余额是软停并把负余额结转到下次充值：https://web.archive.org/web/20260716045147/https://help.openai.com/en/articles/8264644-how-can-i-set-up-prepaid-billing ）· Anthropic Console（usage credits 明写 "billed at standard API rates"：https://support.claude.com/en/articles/14246112-buy-usage-bundles ）· DeepSeek（余额 API 字段直接是 currency ∈ {CNY,USD} + total/granted/topped_up 三个金额，无任何兑换率字段：https://api-docs.deepseek.com/api/get-user-balance/ ）· Kimi 开放平台（available/voucher/cash 三个余额全是「人民币元」且精确到 5 位小数，cash 可为负表示欠费：https://platform.kimi.com/docs/api/balance.md ）· Twilio（连 credit 这个词都不用，余额就是美元，$5/$0 两档告警、$0 挂起：https://help.twilio.com/articles/223135487 ）· Azure（credit lot 的 originalAmount = {currency:USD, value:500.0}：https://learn.microsoft.com/en-us/rest/api/consumption/lots/list-by-billing-profile?view=rest-consumption-2024-08-01 ）· Google Gemini API Prepay（最低 $10、上限 $5,000、1 年过期、余额归零全部 API key 同时停：https://ai.google.dev/gemini-api/docs/billing ）· 阿里云百炼按量（元/百万 Token，免费额度以 Token 数发放：https://help.aliyun.com/zh/model-studio/billing-for-model-studio ）。共同理由被反复表述为「计费透明、无隐藏消费」，且用户是会拿账单做预算/报销/跟上游单价对账的人群。

2. 【类型二 · 一层，但单位是自造点数，锚死在 10 的幂】点数同时是充值单位和消费单位，用户脑子里只需维护一个汇率。GitHub Copilot：2026-06-01 起 premium request 已被 AI Credits 取代，官方明写 `1 AI credit = $0.01 USD`，按 input/output/cached token × 各模型 published API 价折算；套餐额度用「订阅价 ×100」的干净助记（Business $19 → 1,900 credits；Enterprise $39 → 3,900）：https://docs.github.com/en/copilot/concepts/billing/usage-based-billing-for-individuals 。扣子 Coze：2026-01-18 改名时把锚定成 1000 积分 = 1 元（= 1 厘），并在同一张价目表并列「积分/千 tokens」与「元/千 tokens」两列（豆包·2.0·Code 输入 3.2 积分 / 0.0032 元），比例严格 1000:1，用户不需要心算：https://docs.volcengine.com/docs/84458/1585097 。即梦 / 可灵 / 稿定：10 点 = 1 元（1 点 = 1 角）档。OpenAI 消费端 Codex credits 是这一类里的反面：rate card 只给 credits/1M tokens，官方从不公布 $/credit，但每一行除以官方 API 标价都恰好等于 25（1 credit = $0.04，且 25 这个倍数的作用是把 $0.075、$4.50 这类分位小数抬成整数）：https://learn.chatgpt.com/docs/pricing 。

3. 【类型三 · 一层，且不同产品线用不同单位（但不串联）】Kimi 是最清楚的样本：订阅侧是「所有会员功能共享一个额度池、按实际 token 消耗扣除」，只显示百分比、官方不公布任何元换算；充值侧「加油包」则完全以元计价（最低 25 元、余额上限 10,000 元、永不过期、Web 版与 Kimi Code 共享）：https://www.kimi.com/zh-cn/help/kimi-code/benefits 。两个单位并存，但按产品线分叉，用户从来不需要把 A 换成 B。Cursor 同理但更隐蔽：三方模型是美元额度池（Pro $20→$20、Pro+ $60→$70、Ultra $200→$400，超额同价后付费），自研模型池只写「Generous included usage」完全不量化：https://cursor.com/docs/account/pricing 。阿里云百炼 Token Plan 与火山方舟 AFP 形式上是「钱→Credits→按模型抵扣系数→token」，但第二层是一张后台价目表而不是第二种用户可持有的币，用户看到的余额/价签/限额始终是同一个单位。

4. 【类型四 · 真正的两层（钱→币A→币B），且只出现在两个地方】(a) B2B 发票侧：Anthropic 在 AWS/Azure Marketplace 上跑 Claude Consumption Unit，「100 CCU represents $1.00 USD」，token 用量先按美元计价、再按 $0.01/CCU 换成 CCU 报给 AWS；关键是折扣「Applied as fewer CCUs metered」——单位刻度恒定、只让量变不让价变，而且用户在 Claude Console 里看到的仍然是实时美元明细：https://platform.claude.com/docs/en/about-claude/pricing 。Azure 对非美元客户也有第二次换算（creditCurrency vs billingCurrency + exchangeRate + exchangeRateMonth），但汇率锚在外部可核查的公开汇率上并逐笔盖章，而不是后台可调的整数倍率。(b) 游戏/内容商店：Microsoft Points（80 点 = $1、17 种包规格，2013 下线）、Facebook Credits（2013 清零）、Amazon Coins（1 coin = 1 分，2025-08 随 Appstore 关停并对未消费余额退款）三个都死了；还活着的 Robux 是买入 ≈80 R$/$1、兑出 ≈263 R$/$1 的刻意不对称；原神「真钱→创世结晶→原石→祈愿」被 FTC 罚 $20M 并被强制加上「必须能用真钱直接买 + 必须披露兑换汇率」。最有说服力的对照是 Steam：全球最大游戏商店，平台层坚决不发币，钱包余额就是本地法币 1:1。

5. 【压倒性的空白结论】跨五路 40+ 个样本，没有找到任何一个商业软件产品，把「充值得到的币」和「消费扣掉的单位」做成两个不同名字、且都对用户可见。业界文献里唯一贴近的描述是批评性的「double conversion problem」：第一次换算（钱→币）公开稳定，第二次（币→实际工作量）由厂商单方控制且不透明。本项目比它更进一步——两次换算都是 admin 后台可配的旋钮。

6. 【「套餐比直充便宜」在业界是用同一个单位表达的，不需要第二层】Cursor：Ultra $200 → $400 额度（2x）、Pro+ $60 → $70（1.17x）。GitHub Copilot：Pro $10 → 1,500 credits（1,000 base + 500 flex = 1.5x）、Pro+ $39 → 7,000（1.79x）、Max $100 → $200（2x），且 base credits 官方承诺「match your subscription price and they never change」、flex allotment 显式标注「may change over time」——把「诚实的锚」和「可变的优惠」做成两个分别命名、分别声明可变性的桶。Anthropic：预付包 $1000 只收 $700（30% off），在货币计价单位上打折而不新增单位。扣子：¥99/¥199/¥999 档严格 1000 积分/元，入门 ¥39.9 档只有 752/元、企业 ¥980 档只有 352/元——用「套餐给多少」做折扣，不用第二种币。Netlify：Personal 100 credits/$1 vs Pro 150 credits/$1。折扣一律做在「一块钱买多少消费单位」上，从不做在「币换多少点」上。

7. 【界面怎么同时呈现「余额」和「它值多少服务」——四种成型答案】① 双轨（Copilot）：余额用点数计数（`450 / 1,000 AI credits used`），但预算用美元设，官方一句「a $10 budget covers 1,000 AI credits」——锚选对了，UI 就不用解释。② 任务锚定（Kimi）：「一次简单请求（如『推荐一首摇滚歌曲』）约 0.03 元；一次复杂的多步任务（如『规划一周成都到川西的自驾行程』）约 1.6 元」，PPT 生成「约 1-2% 额度」；且加油包购买按钮要到消耗 >80% 才出现，不常驻推销。③ 产出件数（可灵）：660/3000/8000 灵感值直接写成「约 66/300/800 个 5s 视频」。④ 逐笔可审计（Azure/AWS）：每一笔 credit lot 展示来源/生效日/到期日/原始金额/剩余/状态，外加全量流水（AWS 的 Application history 精确到账号、服务、金额）。业界规范侧（Chargebee）的三段式验收清单：Measure（实时余额 + 按功能拆分 + 审计流水）/ Predict（按当前速度还能用多久）/ Control（50%·80%·95% 三档告警 + 封顶）。注意 Predict 用「燃尽时间」而不是「折合多少次调用」——后者是必然被打脸的静态承诺。

8. 【中国合规的真实约束线（与层数无关但被双层放大）】《消费者权益保护法实施条例》（国务院令 778 号，2024-07-01 施行）第二十二条：收取预付款须订立书面合同并约定「预付款退还方式」；「不得降低商品或者服务质量，不得任意加价」；第三款还规定重大经营风险时应停止收取预付款、停业/迁移须提前告知并「有权要求退还未消费的预付款余额」。罚则在第五十条，是 1–10 倍违法所得 / 无违法所得 50 万元以下 / 情节严重责令停业整顿、吊销营业执照——行政责任，不需要用户起诉：https://www.mee.gov.cn/zcwj/gwywj/202403/t20240320_1068830.shtml 。法释〔2025〕4 号（2025-05-01 施行）真正的硬条是第十二条：「未经消费者同意，单方提高商品或者服务的价格、降低商品或者服务的质量，消费者请求经营者按合同约定履行义务并承担相应违约责任的，人民法院应予支持」；第九条把「单方变更合同实质性内容」列为无效格式条款；第十五条规定合同解除/无效时返还剩余预付款并支付利息：https://www.court.gov.cn/zixun/xiangqing/459321.html 。欧盟 CPC《Key principles on in-game virtual currencies》（2025-03-21）直接点名本设计的形态：「mixing different in-game virtual currencies or requiring exchanges should be avoided」，并要求真钱价与币价并列、14 天撤回权对未使用虚拟币不豁免。

9. 【实证事故：改换算口径 = 事实涨价，无一例外引发反弹】Cursor 2025-06-16 把 Pro 从「500 次 fast request」改成「$20 的 API 用量」，沟通不清导致重度用户几个 prompt 就耗尽额度，CEO 于 2025-07-04 公开道歉并对 6/16–7/4 期间的意外扣费全额退款，官方复盘原话：「Based on median token usage, the Pro plan currently covers about 225 Sonnet 4 requests」。即梦 AI：15 秒视频从 45 积分涨到 120 积分（2.67×）、投诉涌入后不到 12 小时被迫改回「限时四折」；4 月全面提价后高级会员月赠积分从 15,000 砍到 6,160，换算成钱单条 15 秒视频从 0.65 元变 5.03 元（约 7.7 倍）——整个过程价签上的「元」一分没动，动的全是「1 积分能买多少服务」：https://www.sohu.com/a/1010914272_115565 。MiniMax 2026-06-01 随 M3 把 Coding Plan 从按次改成按 token，Plus 档 5 小时窗口实测从约 1500 次掉到 300–500 次，被媒体定性为变相涨价，用户最集中的控诉不是涨价本身而是「先斩后奏、无通知」：https://www.tmtpost.com/8025336.html 。Windsurf 2026-03 直接废掉 credit 制改配额，公开理由是用户不敢问简单问题。GitHub Copilot 2026-06 换制后社区反弹措辞是「You will get less, but pay the same price」，GitHub 给出的补救含按比例退款。

## 二、对当前双层设计的评价

【它像谁】形态上最像已经死掉或被罚的一批平台币：Microsoft Points（80 点 = $1、多种包规格、2013 下线）、Facebook Credits（2013 清零）、Amazon Coins（2025 关停退款）、以及被 FTC 罚 2000 万美元并强制「必须能用真钱直接买 + 必须披露兑换汇率」的原神三级币。在世的商业软件里，唯一真正的两层是 Anthropic 在 AWS/Azure Marketplace 上的 CCU（100 CCU = $1.00），但它有三个本设计一个都不占的特征：只出现在 B2B 发票行、比例是干净的 100:1、用户界面上恒定显示美元。开发者工具 / 云 / AI API 这条赛道上，两层的样本数是 0。

【它真实的好处（不能不写）】① 经费层是唯一能吸收上游成本波动的整体缓冲——不改任何一个模型的点数标价，拧一次 recharge_rate 就能全局调价；② 充值面额与消费刻度解耦，可以让消费刻度做到千分之一元的精度而充值数字仍然好看；③ 天然可分池：充值经费 / 赠送经费 / 套餐额度 的有效期、扣减顺序、可退性可以分别设定（DeepSeek 的「优先扣减赠送余额」、扣子的三档有效期都是这么做的）。

【坏处，逐条具体】
1. **毛利变成一道有唯一答案的除法题。** 项目自己把「1 算力点 = ¥0.001 平台真实成本」写进了产品定义，而直充是 ¥1 = 300 点 → ¥1 买到 ¥0.30 的真实成本，加价 3.33×；Pro 月付 ¥1 ≈ 442 点 → 2.26×。后台用量看板已经在向用户展示算力点。第二层币不但没藏住加价，反而把加价率变成了用户做一次除法就能读出的精确数字。真正藏毛利的做法是反过来的——像 Copilot 那样把锚（1 credit = $0.01）钉死、把毛利放进「每次调用扣多少 credit」的费率里。
2. **算力点同时承担两个互相冲突的汇率。** 成本口径是 ¥0.001/点，售价口径是 ¥0.00333/点。同一个词在同一个产品里值两个数，一旦用户对上账（后台已在展示），得到的结论不是「加价 3.33 倍」而是「点值不透明」——即梦踩过的正是这个坑。
3. **两个旋钮都在 admin 后台可调 = 两处可以在不改任何对外标价的前提下改变用户实得价值。** 这正好构成《消保法实施条例》第二十二条「不得降低服务质量、不得任意加价」和法释〔2025〕4 号第十二条的行为要件，而第二十二条的罚则是 1–10 倍违法所得 / 50 万元以下 / 情节严重停业整顿吊照，属行政责任，不需要用户起诉。行业侧的判断更直白：softwarepricing 六宗罪第 4 条原话是「raising the credit-to-dollar ratio is easier than raising the price」——旋钮存在，早晚会被拧。
4. **经费层不承载任何定价灵活性，是纯负担。** 因为「1 算力点 = 固定成本」已经把第二层钉死了，上面那条「整体调价缓冲」的好处实际上取不到——除非放弃算力点的固定成本定义。两者不可兼得，这是设计内部的自相矛盾。剥掉这一条，经费剩下的唯一作用就是让用户多做一次心算。
5. **60、5、300、442 全是坏数字。** 好锚在全部可核查样本里只有两类：10 的幂（$0.01 / $1 / 1000 积分=1 元 / 10 点=1 元 / $1=100 credits）和 25 的倍数（货币里四分之一用得多，数字流畅性研究支持）。300 落在 100 和 1000 之间——既不能移小数点也不能整除，是最难心算的区间；Pro 隐含的 442 点/元用户根本算不出来。面值效应（Raghubir & Srivastava 2002, JCR）说明：当外币面值是本币的大倍数时，人会按面值锚定、对汇率调整不足，系统性低估自己花了多少——短期抬消费，长期在续费/账单时变成 bill shock 与客诉。
6. **退款口径每多一层汇率就多一组争议面。** 第二十二条第三款给了法定的「退还未消费的预付款余额」权利。两层下必须回答：经费余额按 60 折回？已换成算力点但未消费的按 300 折回还是按 60×5？中途改过任一汇率的历史余额按哪一档？
7. **明码标价张力。** 界面只显示「余额 3000 算力点」而无人民币口径，与《明码标价和禁止价格欺诈规定》「一般应当使用阿拉伯数字标明人民币金额」不完全对齐；同时又与「不可反向兑换人民币」的协议条款相互拉扯。
8. **它想达成的目的完全不需要它。** 「买套餐比直充便宜」这件事，Cursor（1.17×–2×）、Copilot（1.5×–2×）、Anthropic（预付包 30% off）、Netlify（100 vs 150 credits/$1）、扣子（752 vs 1000 积分/元）全部是用同一个单位多给来表达的，没有一家是换一个单位、改一个比例。本项目要的 1.47× 落在这个区间正中间，单层完全表达得了。

## 三、可选方案

### A · 单层收口：删掉「经费」，¥1 = 1000 算力点，且把算力点重定义为售价单位

**改法**:取消 recharge_rate 与 credit_to_points 两个旋钮，合并为一个直充汇率 ¥1 = 1000 算力点（1 点 = 1 厘，与扣子 Coze 的 1000:1 同锚）。关键配套：把「1 算力点 = ¥0.001」从**成本口径**改为**售价口径**——毛利不再体现在充值汇率上，而是放进「每次调用扣多少点」的模型点数单价里（点数单价 = 上游真实成本 × 加价倍率 ÷ ¥0.001），这正是 Copilot 的做法：1 credit = $0.01 的锚永不变，毛利藏在 token 费率里。套餐差价改述为「Pro 每周期赠 X 算力点，相当于 ¥1 买到 1,470 点」或直接「订阅额度约为直充的 1.5 倍」。

**对用户**:只剩一个单位、一次换算。1000 点 = 1 元，心算只需移小数点。余额条可以同时给出「剩余 12,500 算力点（≈¥12.5）」，同时满足明码标价与「值多少服务」两个诉求。套餐优势从一个算不出来的 442 变成一句整数话。副作用：数字量级从 3000 点变 10000 点，单次扣减的数字看起来更大（单位效应），需要在文案上配合。

**对运营**:旋钮从 2 个减到 1 个，且这一个应当被当作常量冻结——今后调价一律改模型点数单价，或引入一个显式命名、显式标注「可随模型成本调整」的加成桶（照 Copilot 的 base credits 恒定 + flex allotment 可变）。多池（充值 / 赠送 / 套餐周期额度）仍可保留，但全部使用同一单位，扣减顺序照 DeepSeek「优先扣赠送」或扣子「优先消耗即将过期」公示即可。后台 llmusage 的 cost_micro_yuan 真实成本口径完全不动，只是不再对用户等同于算力点。

**迁移成本**:中。需要一次性把存量经费按当时比例折成算力点入账并向用户出对账说明；改动面覆盖 backend/internal/vip 的钱包/额度/订单、internal/llmusage 的计价与统计、frontend-user 的 settings 计费面板与 admin 用量页。历史订单必须保留原比例快照以备退款争议。建议一次迁移到位而不是分两次改锚——用户对「汇率又变了」的容忍度只有一次。

**它牺牲了什么**:牺牲了「不动任何模型标价就能整体调价」的一键旋钮：今后每次上游涨价都要逐模型改点数单价，或者接受引入一个公开的可变加成系数（多一次沟通成本）。也牺牲了「充值面额好看 + 消费刻度极细」的解耦自由度（1000:1 已足够细，但不如任意比例灵活）。还必须正面回答一个原先被两层模糊掉的问题：用户充值时锁定的到底是什么——是点数数量，还是点数的购买力？

### B · 经费平价化：1 经费 = ¥1，唯一换算放在经费→算力点

**改法**:保留「经费」这个账本与名字，但取消第一层换算：充 100 元得 100 经费（内部按微元整数存储）。唯一对外换算是 1 经费 = 1000 算力点。等价于 OpenAI / Anthropic / DeepSeek / Kimi 的「credits 就是货币余额」范式。

**对用户**:余额就是钱，不需要任何心算；「我还剩多少钱」这个最高频问题零成本回答。但用户仍需在消费侧维护一次换算（1 经费 = 1000 点），相比 A 多一步。

**对运营**:旋钮同样只剩一个。但「经费」这个词失去信息量（它就是元），大概率应当顺势改叫「余额」；一旦改叫余额，本方案就退化成 A 的一个变体。促销只能做成「充 100 送 20 元」这种明账，不能藏在汇率里。

**迁移成本**:低到中。存量经费 ÷60 折成元，用户看到的数字变小 60 倍，需要提前公告并给对照表；账本单位改为微元整数（与 llmusage 的 cost_micro_yuan 口径天然对齐，这一点比 A 省事）。

**它牺牲了什么**:牺牲了「经费不是钱」这层法务隔离感——余额以元计价、可折回，被主张退还的门槛更低（虽然第二十二条第三款本来就给了这个权利，隔离感更多是心理上的）。也牺牲了用充值汇率做促销的空间：所有优惠都必须变成账面上看得见的赠送金额，更合规但也更显贵。

### C · 经费降为内部会计口径：DB 保留两层，UI 只露算力点

**改法**:不动数据模型。充值页、余额条、账单、后台看板一律只显示算力点与人民币等值，「经费」从所有用户可见界面与文案中消失，只存在于后台流水与财务口径。对外只公示一个复合汇率，并同期把它从 300 调整到 1000 算力点/元。

**对用户**:与 A 几乎相同——用户视角只剩一个单位、一次换算。差别是历史流水里可能仍有「经费」字样需要清洗，以及后台/客服看到的账本与用户看到的不是同一套。

**对运营**:两个旋钮仍在后台，只能用制度而非架构约束：必须明文规定「任一旋钮变更 = 涨价公告 + 只对新充值生效」，并把这条纪律写进运维流程而不是靠人记。客服与审计长期面对两套账，排查一笔扣费需要跨两层还原。

**迁移成本**:低。只改展示层、文案与用户协议，无数据迁移，可在一个迭代内完成。适合作为排期紧张时的过渡态。

**它牺牲了什么**:牺牲的是结构性保证。旋钮还在就一定有人去拧——而且拧完之后用户能通过历史账单反推出来，此时的信任损失比一次公开涨价大得多（这正是即梦、MiniMax 两个案例的共同形态：用户炸的不是涨价，是「先斩后奏」）。同时它把技术债转成了组织债：靠纪律维持的约束会随着人员更替失效。

### D · 维持双层 + 四条硬护栏

**改法**:结构不动，加四条不可协商的约束：① 兑换比例按充值批次快照写入流水行，存量余额永久锚定，任何比例调整只对新充值生效（照 Azure credit lot 的 originalAmount / closedBalance / expiration / status 建模，按批次先进先出扣减）；② 余额与每一次扣减都同时显示算力点与人民币等值；③ 用户协议删除任何形式的「有权随时调整兑换比例」，改为「已充值经费的兑换比例自充值之日起固定」；④ 经费不设有效期、未消费余额可退。

**对用户**:静默贬值的风险被堵死，退款口径变得可计算。但 300/442 这两个坏锚和两次心算负担全部保留，「余额还值多少钱」仍然需要用户做两次乘除。

**对运营**:运营复杂度最高：需要按 lot 记账、按 lot 扣减、每笔流水盖上当时的两个汇率；促销、赠送、套餐三种来源各自成 lot；客服要能解释「为什么同样是经费，这两笔能换的点不一样」。同时它保住了唯一的结构性好处——遇到上游成本剧变时仍可对新充值调价。

**迁移成本**:中。要给历史余额补锚定快照（无历史记录的按当前比例封存），实现按 lot 的 FIFO 扣减与展示。工程量与 A 相当。

**它牺牲了什么**:最差的性价比：付出了和 A 差不多的工程量，却拿不到 A 的任何用户侧收益（单一单位、可心算、可对账），换来的只是把一个本来就不该存在的旋钮变成受管制的旋钮。它牺牲的是简洁与心算，保住的是一个按上面分析并不成立的灵活性（因为算力点已被固定成本定义钉死）。

---

## 四、推荐

> 推荐 A（单层收口，¥1 = 1000 算力点，算力点重定义为售价单位）——它同时消掉了本设计三个真实风险（毛利被一次除法算出、两个可静默贬值的旋钮、300/442 这对无法心算的坏锚），而它唯一牺牲的「整体调价缓冲」在当前设计里本来就取不到（因为「1 算力点 = 固定成本」已经把那一层钉死了）；若排期不允许动数据模型，用 C 作为过渡态，但必须同时落地 D 的第①③条护栏，否则过渡态会长期化并保留全部合规敞口。

## 五、容易搞错的事实(引用前必看)

这一节是本次调研最有价值的部分之一 —— 下面每一条都是某个 agent 先写错、被回访推翻后留下的。

1. **「credits」这个词在绝大多数产品里就是美元，不构成第二层。** OpenAI Platform、Anthropic Console、Vercel AI Gateway、AWS、Azure、GCP 的 credits 全部是货币余额。看到别家有 credits 就以为是同类设计，是本轮最高频的误判来源。

2. **AWS credits 不能用钱买，不是充值币。** aws.amazon.com/awscredits 原文：「Promotional Credit may not be purchased for cash, and we and our affiliates do not sell Promotional Credit」，且声明「has no cash value」。它是兑换码型优惠券，不能拿来当「一层充值」的证据，只对「余额展示」和「无现金价值法务话术」有参考价值。

3. **GitHub Copilot 的资料 2026-06-01 已经换代。** 网上大量流传的「$0.04/premium request、code review 13 倍倍率」现在只适用于「remained on legacy premium request-based billing after June 1, 2026」的年费存量用户。当前主线是 1 AI credit = $0.01、按 token 计费。引用前务必看 docs 页顶部有没有 legacy 横幅。

4. **Cursor 的「按 API 原价、无加价」只对个人档成立。** Teams/Enterprise 有一条 $0.25 per million tokens 的 Cursor Token Rate，「applies on top of model API pricing」，连用户自带 key（BYOK）也照收（https://cursor.com/help/models-and-usage/token-rate ）。也就是说「一层 + 用钱计价」并不等于「零加价」——可以用一个与额度正交的 per-token 费率把毛利加回来，不必为了加价引入第二层。另：Cursor 定价页至今一个美元数字都没有（只写「3x Pro limits on Agent」），金额只在 docs 里，是典型的营销页与计费实现脱节。

5. **Cursor 不是一贯一层。** 2025-07 之前用的是「500 fast requests/月、Sonnet 算 2 请求」的请求数单位制，是主动废掉单位制换成美元。迁移方向（单位制 → 货币）比「它一直是一层」这个静态事实更有参考价值。

6. **Claude Code 不是「刻意隐藏金额」。** /usage 屏幕对订阅用户照样显示「Total cost: $0.55」，只是同屏明确标注「isn't relevant for billing purposes」，并声明该数字是本地按标价估算、「may differ from your actual bill」。官方选择的是「给出金额 + 标注与账单无关」，不是隐藏。

7. **Anthropic 用「预付包打折」而不是新增单位来实现「预付更便宜」**：$45→$50、$200→$250、$700→$1000，即在货币计价单位上打折（月度封顶 Pro/Max $2000、Team $3000，超出回原价）。但同一家公司在 AWS/Azure Marketplace 上确实跑 100 CCU = $1 的真两层——分叉发生在渠道（B2C 一层 / B2B 发票两层），不在公司。

8. **Anthropic 曾宣布 Agent SDK 改用美元计价的月度 credit，随后撤回。** 官方页顶横幅：「Update June 15: We're pausing the changes to Claude Agent SDK usage described below. For now, nothing has changed.」网上多篇第三方博客把它写成已生效。引用「Anthropic 订阅侧无美元额度」时要知道这是侥幸为真。

9. **Anthropic 另一条与本项目相关的实现细节：进入 usage credits 后 prompt cache 存活期从 1 小时降到 5 分钟。** 换计费层不只是记账口径变化，会改变实际服务行为——同样的对话在 credits 模式下更费钱。

10. **DeepSeek 余额币种不只有元。** 官方 schema currency ∈ {CNY, USD}，英文文档价签用 $。且赠送余额带过期（granted_balance 定义就是「The total not expired granted balance」），充值余额不带——同单位双池的隐藏第三维度。

11. **扣子的 1000:1 是 2026-01-18 改名时才有的，不是一贯做法。** 旧版套餐比例是 3030 / 843 / 602 积分每元（个人进阶 / 团队 / 企业），是从乱比例迁到 1 厘锚。且**购买侧比例并不恒定**：¥39.9→30,000（752/元）、¥99·¥199·¥999→1000/元、企业 ¥980→345,000（352/元）——用「同一面值单位 + 不同 bundle 大小」做折扣，而不是第二种币。另外「积分是统一结算单位」是营销话术，同页就写了火山方舟大模型、知识库「不支持通过积分抵扣」。

12. **阿里云百炼 Token Plan 的 Credits 不是第二层币，而且现在处于双重促销，任何隐含汇率都是快照。** 官方页写着「预览期间模型调用 Credits 消耗低至 1 折」+「每晚 22:00–08:00 再享 2 折」，消费侧最多有 50 倍浮动。网上流传的「各档汇率不一致（167/182/179）」是把限时促销价与原价混算的产物——按原价算是 125/126/143/179，单调递增的正常量级折扣阶梯。

13. **Kimi 是两个单位并存但按产品线分叉，不是串联。** 订阅侧只给百分比额度池（官方不公布任何元换算），加油包侧完全用元。它可以被引为「一家公司可以同时跑两种计量单位」的证据，但**不能**被引为两层换算的先例——Kimi 全线没有一个「买来持有、再换成别的」的中间币。

14. **Lindy 的 $50 = 5,000 credits（100 credits/$1）常被当作美元平价的正面样板**（Growth Unhinged 原话「dead simple for customers to do the math」），但那是 2026 Q1 之前的结构。当前 v0 定价页已改成不公布任何 credit 数的「standard / 3x / 7x usage」，且超额按标准 credit 费率的 2 倍计。引用它作为「平价可持续」的证据会反向打脸。

15. **Clay 不是双层。** Data Credits 与 Actions 是两个并行、互不换算的计量维度，各自直接以美元标价（Data Credit 起于 $0.05、Action 不到 $0.01）。它的可借鉴点是「按成本来源拆成并行单位、每个单位各自锚定到钱」，不是「叠两层」。

16. **Audible 不是「只给 credit 不给美元」。** 官方帮助文档说明标题页同时显示「Buy with 1 credit」和「Buy for $X.XX」——现金锚点就摆在消费的那一刻。它的可迁移模式是：不公示钱包→币的汇率，但永远在消费点旁边显示现金价。

17. **中国法规里最容易引错的三处**：① 《非银行支付机构监督管理条例》第十五条只有一句「单用途预付卡业务不属于本条例规定的支付业务」，全文没有任何判定标准，不能拿来当「只买自家服务 + 不可反向兑换 + 不可转让 = 安全」的三条件测试；② 《单用途商业预付卡管理办法》第二条把适用范围限定在零售 / 住宿餐饮 / 居民服务三个行业，AI SaaS 不在其中，且它的行业判定实际在附件 1 里（多数引用者没打开过）；③ 上海规定「不限行业 + 覆盖虚拟凭证」是 2019 年就有的，不是 2026 修订新增；2026 版真正新增的是定义里的「分次或者计时」兑付、以及第二十二条把「经营者有权单方变更合同实质性内容」明文列为无效。

18. **法释〔2025〕4 号的 7 日退款不能当冷静期设计。** 第十四条的除外情形包括「消费者订立合同时已经从**其他经营者**处获得过相同商品或者服务」——任何用过竞品或免费档的用户都可能落在除外，且只退本金不含利息。真正的硬条是第十二条（未经同意单方提价/降质 → 按原约定履行 + 违约责任）和第十五条（解除后退还剩余预付款并付利息）。另外该解释全篇以实体卡为架构（记名卡补办、变更经营场所、不限次数服务），是否涵盖线上 AI SaaS 目前无判例，属灰区。

19. **发票是双层制新增的实打实摩擦（需法务/财务确认）。** 若被税务按单用途卡口径认定，售卡/充值环节不征增值税、只能开「不征税」普票（编码 601）、不得开专票，消费环节又不得再向持卡人开票。学术产品的核心付费方（课题组、高校、企业账户）恰恰最需要专票抵扣。一层制按实际消费开票没有这个问题。

20. **「双层能藏毛利」是反的。** 本项目把「1 算力点 = ¥0.001 真实成本」写进产品定义后，第二层币把加价率变成了一道有唯一答案的除法题（直充 3.33×、Pro 2.26×）。真正藏毛利的做法要么是让 credit 没有公开的货币值（Netlify），要么是只暴露服务单位（SendGrid 1 credit = 1 封邮件、Algolia 1 unit = 1000 次检索），要么是锚死单位、把毛利放进每次调用的费率（Copilot）。

## 六、待拍板

1. **「算力点」对用户的定义究竟是成本口径还是售价口径？这是最需要先拍的一条。** 现在它同时是「¥0.001 平台真实成本」和「¥1/300 ≈ ¥0.00333 售价」，两个数并存。必须只选一个对外——选成本口径就等于公开毛利率并且失去调价空间，选售价口径则「真实成本」这个说法必须从所有用户可见文案里撤走（只保留在后台与 llmusage 内部）。这一条不定，A/B/C/D 任何一个方案都落不了地。

2. **是否接受「兑换比例只对新充值生效、存量余额按批次冻结」这条产品纪律？** 如果运营侧无法接受（例如必须保留对存量余额整体重定价的能力），那么双层就不能保留——因为那正是《消保法实施条例》第二十二条与法释〔2025〕4 号第十二条要打击的行为，且是行政罚则（1–10 倍 / 50 万 / 停业吊照），不需要用户起诉。

3. **公司主体注册地是否在上海？** 若是，《上海市单用途预付消费卡管理规定》（2026-01-01 施行）不限行业、定义含虚拟凭证与「分次或者计时」兑付，需按备案 / 资金存管（有规模门槛）做预案，并确保用户协议里没有「单方变更合同实质性内容」的表述。

4. **未消费余额是否承诺可退？按哪一层折算？** 第二十二条第三款给了法定的「退还未消费的预付款余额」权利（至少在停业/迁移场景）。需要明确：经费按 60 折回、还是已换成的算力点按 300 折回、中途改过汇率的按哪一档。单层能把这个问题变成一次乘法。

5. **目标付费人群是否需要增值税专用发票？** 课题组 / 高校 / 企业账户若需要专票抵扣，而余额被按单用途卡口径认定，售卡环节不得开专票会直接卡住转化。需要财务/税务给一个明确口径。

6. **是否引入余额过期机制？** 业界做法差异很大：GitHub 月清零无滚存、OpenAI/扣子增购 1 年、Kimi 加油包永不过期、扣子订阅积分 1 个月。但《单用途商业预付卡管理办法》第十九条对记名卡是「不得设有效期」——若将来被按该口径认定，过期设计会成为存量违规。建议默认不过期，除非有明确的现金流理由。

7. **是否愿意在余额旁并列人民币等值？** 这与「不可反向兑换人民币」的协议条款有心理张力（用户会问：既然显示 ¥12.5，为什么不能退），但同时是《明码标价和禁止价格欺诈规定》与「余额值多少服务」两个诉求的最直接解法。业界的折中是 Audible 模式：不公示钱包→币的汇率，但永远在**消费点**显示现金价。

8. **「套餐比直充便宜」的差价愿不愿意公开表述成整数关系？** 例如「订阅额度 = 直充的 1.5 倍」。如果愿意，单层完全够用；如果坚持要让这个差价不可被用户直接算出，那才需要讨论保留第二层——但那恰恰是欧盟 CPC「should not obscure the cost」原则和消保法明码标价要求指向的行为。

9. **未来是否会有「经费可买第三方服务 / 可转让给他人」的需求？** 一旦有，就从单用途预付滑向多用途预付卡，需要支付业务许可。这个方向如果在路线图上，整个货币层的设计前提要重来。

10. **调价的沟通纪律：是否接受把「汇率/费率变更」当作涨价公告处理（提前公告 + 明确生效范围 + 对已充值用户的补偿口径）？** Cursor 与 GitHub 出事后都提供了按比例退款，即梦与 MiniMax 的舆情核心也都是「无通知」而非涨价本身。这是一条几乎零工程成本、但决定客诉规模的产品制度。
