# 微信 / 支付宝自动续费：能不能做、怎么做、值不值得做

## 结论（先看这五行）

- **微信支付：要申请。** 入口在商户平台「交易中心 → 高级业务」下的扣费服务/委托代扣模板管理（申请权限入口路径为 2025 年二手指引口径，需自行到后台核对）。最硬门槛：**主体必须是企业/政府机构/事业单位/社会组织**（个体户直接出局），且**没有沙箱**，只能拿真钱在生产环境联调。
- **支付宝：要申请，而且大概率申请不下来。** 入口在商家平台 → 产品中心/产品大全 →「商家扣款」→ 立即开通。最硬门槛：**企业注册资本 ≥ 2000 万元 + 已开通收单产品且近半年每月主动支付用户数 ≥ 300 人**。
- **即使批下来，支付宝这条路对我们也是死的**：周期/商家扣款单笔扣款上限 **100 元**，而我们的 Max 月付 ¥269、Pro 年付 ¥590、Max 年付 ¥2690 —— **四个价格档里有三个签不了协议**。
- **明确建议：现在不做。** 做「到期前多次提醒 + 一键手动续费深链」，把触发条件写死：月活跃付费订阅用户稳定 > 300（正好是两个平台的准入线）、月付占比 > 50%、有专人接支付投诉时再重启评估。

## 一、微信支付怎么做

### 1.1 产品定位与命名（先解决"查文档查不到"的问题）

官方产品名在 2024–2026 之间漂移过至少三轮，这是查资料时最先撞墙的地方：

- V2 文档目录里叫 **「委托代扣」**（[产品介绍](https://pay.weixin.qq.com/doc/v2/merchant/4011986647)，标注 2025-08-25 更新，仍在维护，未标下线）
- 商户平台/开放社区侧叫 **「自动续费（原委托代扣）」**
- V3 文档里同族能力被拆成 **「扣费服务（预约扣费）」**「扣费服务（鸿蒙）」等分支
- 同一 docId 在 `pay.weixin.qq.com` 与 `pay.wechatpay.cn` 两个域名下的产品归属标题甚至不一致

**实操结论：按接口路径和参数名对齐文档，不要按产品名搜索。**

「自动续费」不是产品本身，而是委托代扣下的**一种扣款模式**，与「授权扣款」（实时）、「免密支付」（小额免密）、「预约扣费」并列。见[委托扣款模式](https://pay.weixin.qq.com/doc/v2/merchant/4012205799)：「自动续费模式通常用于连续包月、包季、包年的业务场景」—— 会员订阅被产品文档直接点名支持。

### 1.2 技术链路（接口名 + 参数 + 官方 URL）

**签约分两条路：纯签约（先签后扣）与支付中签约（下单同时签约）。**

纯签约（V2，全部在线）：

| 场景 | 接口 | 文档 |
|---|---|---|
| 公众号 | `GET https://api.mch.weixin.qq.com/papay/entrustweb`（MD5 签名，无需证书）| [4011986768](https://pay.weixin.qq.com/doc/v2/merchant/4011986768) |
| H5 | `GET https://api.mch.weixin.qq.com/papay/h5entrustweb`（必传 `clientip`，返回 `redirect_url` 有效期 10 分钟）| [4011987295](https://pay.weixin.qq.com/doc/v2/merchant/4011987295) |
| APP | `POST https://api.mch.weixin.qq.com/papay/preentrustweb` 拿 `pre_entrustweb_id` 再拉起客户端 | [4011986804](https://pay.weixin.qq.com/doc/v2/merchant/4011986804) |
| 小程序 | 无独立 HTTP 接口，`wx.navigateToMiniProgram` 跳微信签约小程序 `appId = wxbd687630cd02ce1d`，参数走 `extraData` | [4011987274](https://pay.weixin.qq.com/doc/v2/merchant/4011987274) |

纯签约的公共必填参数：`appid` / `mch_id` / `plan_id`（模板ID）/ `contract_code`（商户协议号）/ `request_serial` / `contract_display_account` / `notify_url` / `version` / `sign` / `timestamp`。协议主键是**微信返回的 `contract_id`**，也可用 `plan_id + contract_code` 二元组定位。

**H5 纯签约和 APP 纯签约需要在委托代扣权限之外再单独申请**（H5 还要域名报备 + ICP 备案截图，APP 还要 OpenBusinessWebview 权限）。**PC 网站没有纯签约通道** —— 只能扫码进微信内签约页，或走支付中签约。

支付中签约（V3，2025-12-31 更新，说明微信仍在把能力迁 v3）：

- `POST /v3/pay/transactions/jsapi-with-contract`
- `POST /v3/pay/transactions/app-with-contract`
- 文档：[4017019911](https://pay.weixin.qq.com/doc/v3/merchant/4017019911)
- `contract_info` 内必填：`plan_id` / `contract_mchid` / `contract_appid` / `contract_code` / `request_serial` / `contract_display_account`，可选 `contract_notify_url`

扣款：

- `POST https://api.mch.weixin.qq.com/pay/pappayapply`，`trade_type` 固定 `PAP`，无需证书，限速 150 QPS。[4011987377](https://pay.weixin.qq.com/doc/v2/merchant/4011987377)
- **幂等锚点已在渠道侧**：「同一个商户号 + 同一个商户订单号，只会扣款一次」，即 `out_trade_no` 就是幂等键。返回 `ORDER_ACCEPTED` 表示已受理，不得重发。

查询/解约：

- `POST https://api.mch.weixin.qq.com/papay/querycontract`（`contract_state`：0=已签约 / 1=已解约 / 9=签约中）[4011987640](https://pay.weixin.qq.com/doc/v2/merchant/4011987640)
- `POST https://api.mch.weixin.qq.com/papay/deletecontract`（XML / MD5 / 无需证书）[4011987432](https://pay.weixin.qq.com/doc/v2/merchant/4011987432)
- 解约通知的回调地址在**商户后台单独配置**，不在接口参数里。用户在微信侧自助解约也走这条通知。

### 1.3 时序硬规则（决定调度器怎么写）

- **续费扣款延迟 24 小时**：商户调 `pappayapply` 后，微信要等 24 小时才真正扣款。只有首次签约后 12 小时内发起的扣款可立即执行。[4012205799](https://pay.weixin.qq.com/doc/v2/merchant/4012205799)
- 扣款请求时段限 7:00–22:00（24 小时自动扣费模式除外）
- 同一用户同一协议**每天仅可成功扣款一次**；月/季/年模板一个计费周期**最多扣款 2 次**
- 同一商户号 + 同一模板ID + 同一微信号**只能签约一次**
- **没有沙箱环境**。测试模板 0.1 元/笔、每日 100 次上限
- 以上均出自[委托代扣常见问题](https://pay.weixin.qq.com/doc/v2/merchant/4011987907)

另有一条可选链路「预扣费通知模式」：`POST /v3/papay/contracts/{contract_id}/notify`（限 7:00–22:00），当日+次日为扣费等待期，之后 N 个自然日（默认 7 天）为可扣费期，与 24 小时模式二选一。[4011987402](https://pay.weixin.qq.com/doc/v2/merchant/4011987402)

### 1.4 V3 的「预约扣费」不是替代路径

官方标注**仍处灰度测试阶段、暂未开放使用**，且只支持普通直连/普通服务商模式。[4012161141](https://pay.weixin.qq.com/doc/v3/merchant/4012161141)

它的时序与自动续费完全不同（扣费日前一天 8:00–19:30 预约、扣费成功立即解约、失败次日自动解约），是给火车票/演唱会那类"预约后按日扣费"设计的，不能拿来做订阅。

### 1.5 一个会直接改写小程序定价模型的地雷

自 **2026-04-01** 起，微信要求所有涉及虚拟商品（VIP 会员、充值代币、录制课程、音视频等）的小程序**全终端强制接入「小程序虚拟支付」**，不得再用普通微信支付渠道。逾期按违规处理。

也就是说：**小程序内的会员订阅不能走委托代扣。**

费率：标准 17%（Apple 12% + 腾讯技术服务费 5%），腾讯那 5% 在 2026 年限时减免，故 **2026 年 iOS 端实收 12%**（官方社区公告，2026-03-13）。非 iOS 端费率二手源打架（10%/1% 与 20%/15% 两说），**未取证，需自行到小程序后台确认**。

## 二、支付宝怎么做

### 2.1 产品线（三层壳，一条主干）

底层技术只有一条：**签约拿协议号 + 商户主动调扣款接口**。上面套了三层产品：

| 产品 | product_code | 状态 |
|---|---|---|
| 周期扣款 | `CYCLE_PAY_AUTH` | 旧产品。官方明写「已升级为商家扣款，未接入的商家建议使用商家扣款，已接入的可继续使用」 |
| 商家扣款 | `GENERAL_WITHHOLDING` | 2026-03-28 / 04-02 完成升级（官方两处日期自相矛盾），新接入唯一推荐 |
| AI 订阅解决方案 | 底层仍是商家扣款 | 2026 年新推的托管订阅层，API 完全 Stripe 化 |

注意：**官方产品名就是「商家扣款」，不带"升级版"三个字**；支付宝用「旧版本商家扣款」「旧版本周期扣款」指代前代。按"商家扣款（升级版）"去后台搜是搜不到的。

- [商家扣款产品介绍](https://ideservice.alipay.com/cms/site/0j06gs)
- [周期扣款产品介绍](https://ideservice.alipay.com/cms/site/0j2q5o)
- [接入指南](https://opendocs.alipay.com/open/08bpuc)

### 2.2 技术链路

签约：

- 独立签约：`alipay.user.agreement.page.sign`，`personal_product_code` 固定 `CYCLE_PAY_AUTH_P`。[00a05b](https://opendocs.alipay.com/open/00a05b)
  - `access_params.channel` 三取值：`ALIPAYAPP`（支付宝内 H5）/ `QRCODE`（扫码）/ `QRCODEORSMS`
  - `period_rule_params` 子字段：`single_amount`（单次扣款最大金额，**必填，签约时定死**）/ `period_type`（DAY/MONTH）/ `period` / `execute_time`（首次扣款日 yyyy-MM-dd）/ `total_amount` / `total_payments`
  - `period_type=MONTH` 时 `execute_time` 不允许晚于 28 日；`period_type=DAY` 时 `period` 不得小于 7
  - 传 `external_agreement_no` 时 `sign_scene` 必填且不能是 `DEFAULT|DEFAULT`；签约传了什么，后续查询和解约必须原样传回。[sign_scene 取值表](https://ideservice.alipay.com/cms/site/00agk1)
- 支付并签约：`alipay.trade.app.pay` / 小程序 JSAPI 带 `agreement_sign_params`
- **商家扣款升级版只开放"支付并签约"**，独立签约后扣款「仅对部分商家定向开放」，需咨询 4007585858

扣款：`alipay.trade.pay`，`product_code` 必填且固定 `GENERAL_WITHHOLDING`，协议号放 `agreement_params.agreement_no`（传了协议号就不用再传 `scene` 和 `auth_code`）。

**支付宝不会到期自动扣款** —— 每一期都必须商户主动调 `alipay.trade.pay`。扣款结果以 `alipay.trade.query` 的 `trade_status`（`TRADE_SUCCESS` / `TRADE_FINISHED`）为准。

延期 / 解约 / 查询：`alipay.user.agreement.executionplan.modify` / `alipay.user.agreement.unsign` / `alipay.user.agreement.query`。

**关键限制：`executionplan.modify` 的请求结构体只有 `AgreementNo` / `DeductTime` / `Memo`，没有任何金额字段。** 签约时定死的 `single_amount` 事后改不了 —— 涨价、换档、周期变更全部只能解约重签，等于重走一遍用户授权，转化率归零。

### 2.3 时间与额度规则（决定成本模型是否成立）

- **单个协议单笔扣款限额 100 元；标准模式下对每个用户单日 ≤ 1000 元、单月 ≤ 30000 元。接口参数只能往下收紧，无法提额，提额需咨询商户客服 4007585858。** [额度介绍](https://opendocs.alipay.com/support/01rg28)
- 扣款须在北京时间 **7:00–22:00** 发起（[使用规范](https://opendocs.alipay.com/b/06aql9) 4.8）
- 周期扣款：`execute_time` 前 **5 天**可发起扣款；商家扣款升级版收紧为**下次预计扣款时间前 48 小时**
- 两次扣款间隔建议不小于 30 天
- 支付并签约时，**优惠后金额不得低于正价的 1/3**，否则用户续费时会扣款失败
- **暂不支持沙箱调试**，只能真实账号真实签约联调
- 扣款失败重试：官方建议只重试 2 次，始终扣不到就停止提供服务。[01rg2k](https://opendocs.alipay.com/support/01rg2k)
- 撤销（`alipay.trade.cancel`）后当期还能再扣一次；**退款（`alipay.trade.refund`）后当期不允许再扣**
- **退款不会解约** —— 退款只退这一笔，协议仍有效，下期照扣。这是把一次退款升级成投诉的标准剧本

用户侧解约入口固定在「支付宝 App → 我的 → 设置 → 支付设置 → 免密支付/自动扣款」，商户**无法隐藏或关闭「关闭服务」按钮**（官方明文回答：没有任何参数或方式可以控制）。[01rg2b](https://opendocs.alipay.com/support/01rg2b)

### 2.4 AI 订阅解决方案：唯一可能绕开门槛的路，但全是未知

2026 年新推的托管订阅层（`aipay.alipay.com`），API 形态是 Stripe 式的 `product` / `price` / `customer` / `subscription` / `coupon`：`alipay.trade.product.create` / `price.create` / `customer.create` / `subscription.create` / `subscription.modify` / `subscription.query`。[introduce.md](https://aipay.alipay.com/docs/subscribe/introduce.md)

**它对我们有三个直接相关的特征：**

1. **扣款由支付宝执行**：到期前 2 天平台发扣款预通知、到期前 1 天扣款、失败按算法自动重试、到期仍未成功则不再扣款并自动解约。合规提醒义务被平台接走了一大半。
2. **`recurring.interval` 支持 `YEAR`**（商家扣款只有 DAY/MONTH），并支持 `trial_period_days` 试用期、按比例结算的升降级、托管用户门户。
3. **准入按 MCC 类目白名单**，而白名单里有 **B0113 信息检索服务 / B0121 软件开发服务 / B0120 互联网数据服务 / B0125 其他在线应用 / B0112 在线工具** —— 学术检索 + AI 写作 SaaS 精准落在这个族里。订阅场景新签用户数上限 1000 个，需申请扩容。

但三个致命未知，**全部未取证，必须自行向支付宝业务人员书面确认**：

- **AI 订阅是否仍受商家扣款的「单笔 100 元」限额约束？** AI 订阅文档全文不提额度，但明写底层用商家扣款。如果限额继承，Max 月付和所有年付照样签不了，这条路白走。
- **通过 AI 订阅入口申请，是否可豁免 2000 万注册资本要求？** 文档未交代，而这直接决定中小 AI 产品能否接入。
- **合规口径冲突**：《商家扣款产品使用规范》5.3.1 把「0.01 元试用 xx 天」「首月 0 元体验」「免费试用会员 XX 天」明确列为违规诱导表述，而 AI 订阅营销工具包的 `trial_desc` 默认文案恰恰是「免费试用{n}天」。是否因签约页由支付宝托管而豁免，需确认。

另外 AI 订阅**暂不支持服务商代开发**，且所有订单**按不同账期资金管控，管控期间资金处于「止付」状态**，账期由支付宝根据经营情况动态调整。

## 三、申请与资质

### 3.1 微信侧

**主体门槛（硬）**：仅支持企业、政府机构、事业单位、社会组织类型的特约商户及普通特约商户。**个体工商户不可申请。** 商户号需有微信支付认证过的客服电话。

**费率条件（需自行核实）**：2025 年微信开放社区《商户后台自助申请指引》写有「商户号入驻类目费率与标准费率一致（即不可以享受特殊优惠费率）」。**但该页需微信登录，未能一手取证**；且 2025 年两份更新的官方规则（《免密服务运营规则（20250310版）》、财付通 2025-07-28 管理规则调整公告）重写申请条件时**都不含这条**，因此不能断言 2026 年仍适用。**未取证，需自行到商户后台确认。** 另外网上流传的"享受优惠费率的商户放弃优惠即可申请"是推论，没有任何来源支持，别当路径规划。

**费率本身**：委托代扣/免密支付**不设独立费率**，沿用商户既有《微信支付服务协议》约定的类目费率——这条有一手证据（《微信支付免密服务协议（普通商户）（20240930版）》2.1 条明文「相关条款以原协议为准」）。公开可取证的官方数字是**标准费率 0.60%**、优惠活动区间 0.2%~0.6%、进件费率枚举 0.38%~0.6%。**网上流传的"0.6%–1%"没有任何官方页面支持**，微信也不公开逐类目费率表，应视为坊间口径。

**行业开放范围**：**没有公开的封闭行业白名单。** 现行《免密服务运营规则（20260614 版）》根本不枚举行业，只写「场景应当为合法合规的、付款频率或者额度等条件事先约定且相对固定的特定场景，或其他小额便民服务业务场景，**具体以微信支付核准为准**」+「微信支付有权基于商户主体的风险、资质、运营情况以及所提交的资料审核开通申请」—— 即**逐案审批**。

唯一能在官方页面取到的行业清单在跨境开发者中心：「互联网共享/租赁充电宝、公共事业、智能冰柜、话费、交通行业、线上内容行业」，其中**既没有"教育"也没有"工具"**。网上流传的"餐饮/教育/运动/公益/金融/生活缴费/线上及虚拟行业（工具）"九项清单只在第三方博客出现，同一博客另一篇给的还是完全不同的第三套分类。**学术检索 + AI 写作 SaaS 能否归入某个已开放行业，没有任何依据可以预判，只能提交申请试。**

**交易量分档 —— 这不是审核门槛，是开通后的结算周期分级**（很多资料把这点写错了）：

| 情形 | 条件 | 结算周期 |
|---|---|---|
| 一 | 近 4 自然周有效订单去重用户数 ≥ 300 且升级投诉率 ≤ 0.05% | 不调整 |
| 二 | **已在微信支付持续经营一段时间**，去重用户数 20–300 且升级投诉率 ≤ 0.1% | 调整为 T+7 |
| 三 | **使用新主体经营、无持续经营记录**（去重用户数 ≤ 20） | 调整为 T+14，不设投诉率要求 |

情形二、三均附「商户若已有更长结算周期设置，取更长者」。指标名是**「升级投诉率」**，是微信的特定口径，不等于普通投诉率。

**要点：低流水不是一票否决，代价是结算周期被拉长；真正的一票否决是主体类型。** 另外，网上流传的「近 3 个月主动支付日交易笔数超 1000 笔 → T+1」是**张冠李戴** —— 那 1000 笔出自自助申请上线前的 BD/邮件报备自查清单，与结算周期毫无关系，且原始出处自带免责「不是绝对的，以对接 BD 的要求为准」。

**申请入口**：
- 模板路径「高级业务」这一级**有官方文档背书**：v3《开发接入准备》（2026-05-19 更新）明写模板操作入口在「商户平台后台的高级业务栏目下」。[4012161141](https://pay.weixin.qq.com/doc/v3/merchant/4012161141)
- 权限申请的四级路径「产品中心 → 我的产品 → 支付拓展工具 → 委托代扣」**只有 2025 年二手指引来源，2026-08 未复核。未取证，以商户平台实际菜单为准。**
- **自助入口是灰度增量通道，不是主口径。** 同一份 2026-05-19 的官方文档仍写「若商户号当前无委托代扣权限，需联系对接的运营同学协助评估」—— BD/运营评估这条老路仍是官方文档的主口径。
- 灰度未开放的商户可填登记表，「登记后一个工作日内开放**申请入口**」—— 开的只是入口，**权限本身审核一般 5 个工作日，模板审核另计**。别把这个跟 v3 文档里「预约扣费处于灰度测试、暂未开放」混为一谈，那是扣费模式的灰度。

**服务商不是捷径**：官方明确「服务商没有特殊权限，不满足申请要求同样会被驳回，不存在 100% 包过」，并对收费代办发出诈骗警示。

**最高频被拒原因**：产品交互图与实际页面不一致。交互图必须是单份文档内的完整闭环：首页 → 我的 → 会员续费页 → 支付 → 成功页 → **取消自动续费界面截图**。

### 3.2 支付宝侧

**这里是整个方案的死结。**

商家扣款（新接入唯一推荐）准入条件，官方原文：

- 仅支持支付宝**企业账号**接入（商家分账那档才额外接受个体工商户）
- **企业注册资本 ≥ 2000 万元人民币**
- **已开通支付宝收单产品且近半年每月主动支付用户数 ≥ 300 人**（同个工商主体下任一支付宝账号，不含收钱码交易）
- 企业无经营风险（行政处罚、股权冻结、股权质押、动产抵押等）
- 支付并签约的 APP 场景需先开通 APP 支付（移动应用须已上架）；小程序场景需先开通 JSAPI 支付

注意口径校正：**2000 万 + 300 人并非本次升级新增** —— 旧版商家扣款就已是同样标准。真正被抬高 20 倍的是相对「周期扣款」的基线（100 万 → 2000 万），且新增了原先不存在的活跃用户数门槛。

**周期扣款（旧产品）的注册资本门槛，官方页面之间自相矛盾，必须自行核实**：
- `ideservice.alipay.com/cms/site/0j2q5o`（产品介绍页）写「在线提交营业执照，注册资本大于等于 **100 万**人民币」
- `opensupport.alipay.com` 的《周期扣款准入条件》FAQ 写「注册资本大于等于 **1000 万**人民币」+「申请企业与支付宝合作年限 1 年及以上」
- 第三方 ISV（Ping++）文档跟的是 1000 万口径
- **未取证：周期扣款当前是否仍向新商户开放签约。** 官方措辞只是「建议使用商家扣款」「已接入的可继续使用」，不是「停止受理」；真正的闸门在需登录的商家平台签约页。**如果周期扣款仍可开、且门槛真是 100 万，这是唯一现实的低门槛路径，值得花一通电话（4007585858）问清楚。**

**申请路径**（官方 5 步，注意别漏第 2 步）：创建应用 → **配置应用（接口加签方式、应用网关为必填）** → 上线应用 → 绑定商家账号（官方标注为「可选操作」，仅当要用支付/资金类产品时才必须）→ 商家平台 产品中心/产品大全 的产品详情页点「立即开通」提交材料。

「不满足准入条件原则上不予准入，特殊需求联系商家客服 4007585858」这句出自 `opendocs.alipay.com/support/01rg25`（**不是** quickstart 页），且仅有搜索引擎索引快照，**未一手取证**；「8:00-24:00」这个时段更是完全没有官方页面佐证。

**费率与结算**：单笔 0.6%~1%（各行业不同，以签约协议为准），退款时手续费一并退还，退款周期 12 个月。**「新签约该产品未满 90 日或连续交易未满 30 日的商家，资金于次日结算」** —— 注意是「或」，老商户只要连续交易断档不满 30 天同样会被打回 T+1。

**服务质量硬指标**（[0cbc33](https://opendocs.alipay.com/b/0cbc33)）：近 7 天投诉率 ≥ 1% 或升级投诉率 ≥ 0.1% 或 72h 投诉完结率 < 90% → 首次暂停新签 7 天、二次 21 天、三次**永久暂停新签**。

### 3.3 跨平台判断

有一条常见的错误说法必须点掉：**"支付宝门槛低于微信，申请不下微信可以先上支付宝"是完全反的。** 支付宝对小主体更不友好（2000 万注册资本 + 300 活跃用户 + 人工审核，不存在自助开通），微信没有注册资本门槛，低流水只影响结算周期。

**微信 = 够得着但要碰运气（行业逐案审批、主体必须是企业）；支付宝 = 门槛上基本够不着，且就算够着了也被 100 元限额卡死。**

## 五、我们仓库要改什么

### 5.1 底座盘点：好的部分

**支付回调 → 履约是现成的，可以直接复用，这是最省的一块。**

两条回调最终都汇进 `vip.OrderService.fulfill`（`backend/internal/vip/order.go:371-463`），幂等真源是「事务内 `FOR UPDATE` 锁 orders 行 + `status=='paid'` 短路（:392）+ 条件 UPDATE 的 `RowsAffected==0` 兜底（:416-426）」。代扣成功后直接走这条路径即可，不需要新写履约。

**订阅计价也是现成的**：`computeSubscription`（`order.go:186-271`）是纯函数，已有 new/renew/upgrade 三态、自然月/年 `AddPeriod`、升级按剩余天数补差 + 定价基准失效硬闸。自动续费只用 renew 分支（:263-270）。

**定时任务设施可直接复用，不需要引 cron 库**：`backend/internal/common/cleanup/cleanup.go:439-487` 提供 `runDaily(hour,minute)` / `runPeriodic(interval)`，且已有 5 个「函数型注入钩子」先例（`SetPendingOrderCanceller` 等，:56-71 / :100-120 / :146-150），注入点在 `backend/cmd/server/bootstrap.go:538`。分布式互斥有 `cache.RunWithLock`（`backend/internal/common/cache/redis.go:385-460`，随机 owner token + 每 ttl/3 自动续期 + owner-scoped 释放）。

**回调路由有现成的公开组**：`backend/cmd/server/routes_scholar.go:18-32`（`registerPaymentCallbackRoutes`，无鉴权），签约/解约通知回调直接加在同处。

**通知通道就绪**：`backend/internal/vip/notify.go:41-69, 81-120`，站内信（可靠）+ 邮件（best-effort，品牌模板）。

**测试支付通道可以先跑通履约侧**：`backend/internal/vip/billing_handler.go:20-31, 279-302`（`PAYMENT_TEST_ENABLED`，`GIN_MODE=release` 时硬关），不用等代扣权限批下来。

### 5.2 底座盘点：坏的部分

**一方 Go 代码里自动续费是零起点。** 对 `backend/internal` + `backend/cmd` 全量 grep `自动续费|周期扣款|委托代扣|papay|agreement.*page.*sign|auto_renew` 命中数为 **0**。

三个同名陷阱，别搞混：
1. `user_wallets.credit_autopay_enabled`（迁移 0094，`backend/internal/vip/quota.go:844,857`）是「周期额度用完后自动用**已充值的经费余额**继续跑」，**不向支付网关发起任何扣款**，与自动续费完全无关。
2. `user_subscriptions.auto_renew`（`docker/mysql/migrations/0001_baseline.sql:1301`）挂在 stranded 表上，无任何 Go 代码读写，CLAUDE.md 明令新功能不要依赖。**不要复活这张表** —— 它的 `plan_code`/`status` 语义与现行 `users.vip_*` 真源冲突。
3. `payment.Provider` 统一接口（`backend/internal/payment/provider.go:101-118` + Registry :126-155）是**零实现零注册的死代码**，全仓无 `payment.Register(` / `payment.Get(` 调用。**别指望它能降低新渠道接入成本**，支付宝和微信要各写各的。

**微信 v2 与我们刚做完的 v3 是两套密码学。** papay 系列是 XML + MD5 + 无需证书；我们的实现是 JSON + SHA256withRSA（`backend/internal/payment/wechat_pay_crypto.go`）。考虑到上次踩过 `SignPKCS1v15` hash 传 0 的坑，新签名代码的风险要按"重来一次"估。

**支付宝侧只有两个 method**：`alipay.trade.page.pay` / `alipay.trade.wap.pay`（`backend/internal/payment/alipay_service.go:85-89, 225-247`），`biz_content` 里没有任何签约参数。

**渠道配置表缺列**：`alipay_configs` 只有 8 个业务列（`0001_baseline.sql:80-95`），`wechat_pay_configs` 经 0105 补到含 `merchant_certificate` / `wechatpay_public_key_id` / `validation_status` 等 —— 两者都缺代扣所需的**模板ID / plan_id / 签约回调地址 / 场景码**列。

**退款链路是登记式的，且没有"解约"这个动作可调**。`backend/internal/vip/refund.go:23-36` 头注释：「系统内标记 + 权益回收，不调网关。管理员先去支付宝/微信商户后台把钱退掉，回到管理台登记」。而自动续费最典型的处置就是「退款 + 解约」，且**支付宝退款不会解约** —— 在没有解约动作的系统里，退完款下期照扣，这是把投诉升级的标准剧本。

**顺带一个可以立刻修的注释漂移（与自动续费无关，但值得记）**：`backend/internal/payment/wechat_pay_handler.go:319-322` 的函数文档注释写「…断言事件类型/币种/订单归属/金额 → 去重锁 → 履约」，但实现里去重锁在 `:392`、订单查找在 `:422`、金额校验在 `:446` —— **订单归属和金额都在锁之后**。注释与代码不符，按注释理解这段安全序会被误导。

### 5.3 三个会打架的既有护栏

1. **`CreateSubscription` 的「单活跃订阅单」硬约束**（`backend/internal/vip/order.go:123-165`，判定在 :149-151）：清理 >2h 的 stale pending 后，只要还有 pending 订阅单就返回 `ErrPendingOrderExists`。这个约束是为堵「挂低档年度续期单 + 升档 + 再支付旧单」的套利。

   冲突是**双向**的：系统建续费单会在用户有 <2h pending 单时被拒；更麻烦的是**系统建的续费单本身就是一条 pending 订阅单**，在它 pending 期间（微信 v3 受理扣款是异步回调，pending 窗口必然存在）会阻塞用户自己的下单/升级最长 2h，以及扣款失败后的重试建单。

2. **`cleanStalePendingOrders`** 每天 04:45 把 >24h 的 pending 单打成 expired —— 微信 24 小时延迟扣款的单子会踩线。

3. **`voidPendingUpgradeOrders`** 会在续期履约时作废用户在途升级单。

**这三条都必须为"系统自动建的续费单"开豁免路径。** 注意 `order_source` 这个字段**在仓库里不存在**（全量 grep 零命中，orders 表建表 `0001_baseline.sql:630-664` 及 0016/0020/0107 的所有 add_column 都没有来源列），它是建议新增，不是既有设计。可选方案还有：给 `CreateSubscription` 加 `isAuto bool` 入参、复用已有的 `sub_action` 列、或让续费走独立建单函数。

### 5.4 索引：一个已经在烧的洞

`users.vip_expires_at` **没有任何索引**。已实测确认：

- 迁移全目录 grep `vip_expires_at` 只命中 `0008_vip.sql:14` 一条 `add_column_if_not_exists`，无任何 `add_index`
- 线上库 `SHOW INDEX FROM users` 返回 12 条索引，无 `vip_expires_at`、无复合索引前缀、无生成列
- 应用代码零 `AutoMigrate` 调用，schema 唯一真源就是迁移文件

**而且这个全表扫今天已经在跑**：`backend/internal/vip/quota.go:992-1002`（`RealignExpiredMembershipWindows`）的扫描 SQL 由 `cleanup.go:162-168` **每 5 分钟**调度一次，EXPLAIN 实测 `type: ALL, possible_keys: NULL, key: NULL, rows: 398`。

当前 398 行代价可忽略，属容量前置项而非阻塞项。但如果做自动续费，扫描口径**更应该落在新的签约表上**（只有签过约的才需要扫，基数小几个数量级），而不是 users。

## 六、建议：现在不做

三条硬约束，任何一条单独成立都足以否掉，三条同时成立：

**一、准入过不去（或过去了也没用）。** 支付宝 2000 万注册资本 + 近半年每月 300 活跃付款用户，基本无解；就算走周期扣款旧口径（100 万 / 1000 万，官方页面自相矛盾，且是否仍受理新签约未取证），也被 100 元单笔限额卡死四档里的三档。微信没有资本门槛，但主体必须是企业、行业逐案审批、没有公开白名单、**没有沙箱**，且申请周期（权限 5 工作日 + 模板另计 + 被拒重来）不可预测。这段时间是纯沉没成本。

**二、合规成本固定，不随规模摊薄。** 上线自动续费 = 必须同时建：短信通道（深圳指引明确站内信不达标）、扣款前 5 日提醒调度、双取消入口（站内 + 平台）、每次扣款单独提醒、协议对账、涨价前置流程（微信要求提前 60 日报备 + 提前 30 日取得明示同意）。这套东西对几百个订阅用户，边际收益极低。

**三、投诉风险高度不对称，且伤的是主业务。** 微信违规处罚可以打到"关闭商户主体或商户号下部分或全部支付权限"，支付宝三次触发指标即永久暂停新签。小基数下几笔投诉就能把比率打爆。而我们的退款链路是"人工去网关后台退 + 管理台登记"，系统里**根本没有解约这个动作可调**，退完款下期照扣 —— 这是投诉升级的标准剧本，而且是我们自己造的。

**收益侧没有证据支撑。** 找不到任何可信的国内公开数据能量化「自动续费相对手动续费提升续费率 X%」，全是定性说法。反倒有反向证据：海外 benchmark 显示 involuntary churn（扣款失败导致的非自愿流失）占订阅流失总量 20–40%，行业中位追回率仅 47.6%，要做到 70–85% 需要分层 dunning 体系。也就是说自动续费本身会引入一类新流失，还要再建一套系统去补。（口径差异需注意：海外主因是信用卡过期，国内支付宝/微信由平台维护绑卡，主因是余额不足与用户已解约，不能直接套用数值。）

**重估触发条件（建议写死在决策记录里）**：月活跃付费订阅用户稳定 > 300、月付占比 > 50%、有专人处理支付投诉 —— 三条同时满足再启动申请。

**唯一值得现在花时间的事**：打一通 4007585858，问清两件事 ——（1）AI 订阅解决方案是否豁免 2000 万注册资本、是否仍受 100 元单笔限额约束；（2）周期扣款旧产品当前是否仍受理新商户签约、真实注册资本门槛是多少。这两个答案能把整个判断翻过来（AI 订阅的 MCC 白名单里 B0113/B0121/B0112 精准覆盖我们的类目，且它把扣款前通知义务和重试逻辑都由平台接走了）。这通电话成本 10 分钟，是全篇 ROI 最高的动作。

## 八、如果决定不做：替代方案与成本对比

**方案：到期前多次提醒 + 一键手动续费深链。**

实现：`cleanup.go` 加一个 `runDaily` 任务，扫 `users.vip_expires_at`（先补 `idx_vip_expires_at`），在 T-7 / T-3 / T-1 各发一次站内信 + 邮件（`notify.go` 现成），正文带一条深链直达 `subscribe-dialog` 且预选好用户当前档位与周期，点进去就是支付二维码。

| 维度 | 自动续费 | 到期提醒 + 一键续费 |
|---|---|---|
| 前置申请 | 微信 2–4 周（可能被拒）、支付宝基本不可行 | 无 |
| 后端工作量 | 2–3 周（单渠道）/ 4–6 周（双渠道） | 2–3 天 |
| 新增 DB 对象 | 2 张表 + 5 个索引 + 4 个字段 | 1 个索引（且今天就该补） |
| 新增外部依赖 | 短信通道（合规必需） | 无（复用站内信 + 邮件） |
| 新增密码学代码 | 微信 v2 XML+MD5 全套 | 无 |
| 联调条件 | **两平台均无沙箱**，只能真钱真签约 | 现有测试支付通道即可 |
| 价格档兼容 | 支付宝下 4 档只能签 1 档 | 全档位无限制 |
| 涨价成本 | 微信提前 60 日报备 + 30 日明示同意；支付宝需解约重签 | 改配置即可 |
| 合规负担 | 三层法规 + 两平台规则 + 短信提醒 + 双取消入口 | 无（提醒本身不构成扣款行为） |

| 退款/解约链路 | 必须先补齐（现在没有解约动作） | 沿用现状 |

| 续费转化 | 无国内可信数据；且引入 involuntary churn | 未知，但可作为基线测量 |

**这套方案还有一个隐藏价值：它能给你手动续费率的基线数据。** 现在关于"自动续费能提升多少续费率"的所有说法都是定性的，做完提醒方案跑三个月拿到基线，未来重估时才有东西可比 —— 否则永远只能靠感觉决策。
