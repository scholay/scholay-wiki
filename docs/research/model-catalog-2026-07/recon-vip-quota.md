## summary
「每日额度」是 backend/internal/vip 内一套「统计与限额分离」的 Redis 计数体系,全部 AI 功能共用一个 raw-token 池。核心在 quota.go:真实消耗 used 记在 `quota:tokens:<uid>:<YYYYMMDD>`(quota.go:96-99,AddUsage IncrBy 单调累加、首写设 25h TTL,quota.go:286-298),额度窗口起点 base 记在 `quota:base:<uid>:<YYYYMMDD>`(quota.go:157-161),限额判定用「窗口内消耗 = used - base」(tokenWindowUsed,quota.go:192-197),而非直接拿统计当闸。0 点滚动没有任何定时任务——key 名含日期,跨 0 点自然换 key 即自动满血(quota.go:96 注释),25h TTL 防时钟漂移后自动清理。上限 ceiling 由 billing_config 单行表推导:DailyCeiling = FreeDailyTokens × ProMultiplier(Pro)× MaxMultiplier(Max 相对 Pro 翻倍),≤0 视为不限(-1)(billing_model.go:73-93);默认 Free=20 万/Pro=5×/Max=25×(config.go:20-23),tier 单一真源是 EffectiveTier(service.go:91-105,付费且未过期才生效,到期读时自动回落 free)。三个闸门:CheckDailyQuota(严格,quota.go:205-224)、CheckDailyQuotaOverdraft(上限放宽到 ceiling+透支带,quota.go:251-268;透支带 = max(ceiling×15%, 20 万),billing_model.go:98-113)、RemainingBudget(只读返回 soft/hard 剩余,给 agentbridge 盖 budget 帧,quota.go:230-245)。「满血」三条路径都只动 base 不动 used:手动重置 ResetQuota(消耗 ResetCostCredits=60 经费,base=当日 used,quota.go:330-410,带进程内 256 分片锁 + Redis SETNX `quota:reset:<uid>:<day>` 双层防双扣)、升级免费满血 ResetBaselineOnUpgrade(quota.go:418-435,由兑换码 service.go:146 / admin 直授 service.go:311 / 订阅履约 order.go:349 调用)、每日 00:00 自然换 key。Redis 挂时有界 fail-open:进程内 fallbackCounter 按日字符串滚动清零(quota.go:128-155)。前端展示字段在 TokenStatus{used(窗口口径)/ceiling/percent/unlimited/consumed_today(真实统计,重置不清零)}(quota.go:450-456)与 Overview{tier/expires_at/token/credit/auto_reset/reset_cost}(quota.go:459-466),经 GET /user/billing/overview(billing_handler.go:27)与 /user/membership(handler.go:25)下发;UsageCalendar 另从 MySQL llm_token_usage 聚合当月按日用量 + daily_ceiling 参考线(quota.go:475-485、billing_handler.go:75-87)。执法点全仓共 12 处业务闸 + 3 处预算盖章:CheckDailyQuotaOverdraft 在 smartsearch/claw/prism 三个 WS 对话 feature 的 PreUserMessage(经 agentbridge.StandardHooks,hooks.go:110);CheckDailyQuota 在 peerreview(向导推进×1、提交×1、重试×1)、prism 非对话路径(inline_review/revision/planner)、ai handler(论文矩阵分析、翻译 SSE);RemainingBudget 在三个 spec 的 BudgetProvider,由 hub.go:995 stampBudget 盖进 user_message 帧,agent 容器 ws.ts/turnLoop.ts 消费做自我配速与优雅收尾。唯一扣减点是 AddUsage,由 llmusage.SetObserver 在 bootstrap.go:388-391 接线;bootstrap.go:375-385 启动断言 5 个付费功能 VIPChecker 必须接线否则 panic。若改 7 天滚动窗口:闸门函数签名与全部执法点可不动(口径收敛在 tokenWindowUsed/DailyCeiling 两个内部函数),主要工程量在 vip 包内部(多 key 求和、TTL 拉长、base 语义按日分桶化、fallbackCounter 环形化)+ billing_config 加旋钮 + 前后端「00:00 恢复」文案全改。

## keyFacts
- Redis key 设计:used=`quota:tokens:<uid>:<YYYYMMDD>`(backend/internal/vip/quota.go:96-99),base=`quota:base:<uid>:<YYYYMMDD>`(quota.go:157-161),重置分布式锁=`quota:reset:<uid>:<YYYYMMDD>` SETNX 5s TTL(quota.go:59-65);走 cache.GetRedisPersist() 持久池
- 0 点滚动 = key 含日期自然换 key,无定时任务(quota.go:96 注释「跨 0 点自然换 key = 自动满血」、文件头注释 quota.go:15);TTL 25h 防时钟漂移(AddUsage 首写 quota.go:294-297;base 写 quota.go:395、430)
- 统计与限额分离:tokenUsed 读真实累计(quota.go:164-175,永不被重置删减),tokenBaseline 读窗口起点(quota.go:178-188),tokenWindowUsed = used - base clamp≥0(quota.go:192-197)——所有闸门与额度条都用窗口口径
- CheckDailyQuota(严格闸):Enabled 关/ceiling<0/未登录放行;windowUsed<ceiling 放行;超限直接回 NewQuotaError 友好文案,自动扣经费重置已下线(quota.go:205-224)
- CheckDailyQuotaOverdraft(透支闸,3 个 WS 对话 feature 用):唯一区别是上限放宽到 ceiling+OverdraftTokens,保证跨线那一轮总能起跑(quota.go:251-268)
- OverdraftTokens = max(ceiling×15%, 200_000),不限额时 0;透支不结转,随日窗口自然归零(billing_model.go:98-113)
- RemainingBudget 返回 (soft=到日上限剩余, hard=到上限+透支带剩余, unlimited);由 hub.go:995-997 调 stampBudget 把 {budget:{softRemaining,hardRemaining}} 盖进 user_message 帧(agentbridge/ws.go:666-675),agent 容器 parseTaskBudget(agent/src/server/ws.ts:40)+ budgetDisclosure/wind-down(agent/src/turn/turnLoop.ts:32-39)消费(quota.go:230-245)
- AddUsage 是唯一扣减点:IncrBy 当日 key,best-effort 不阻塞;附带越线可观测(prevWin<ceiling≤curWin 时记一笔,overshoot>25% 升 WARN)(quota.go:272-321);接线在 bootstrap.go:388-391 llmUsageService.SetObserver→vipService.AddUsage
- ResetQuota(POST /user/billing/reset,routes_user.go:127):resetInternal 流程=双层锁(进程内 256 分片 mutex + Redis SETNX)→resetNotNeeded 首判→钱包余额预检→TOCTOU 二判(防升级瞬间白扣)→先写 base=当日 used(Redis 失败不扣费)→后扣 ResetCostCredits 经费(扣费失败=送免费重置只告警)(quota.go:330-410);默认 60 经费(config.go:31)
- ResetBaselineOnUpgrade(免费满血,不收经费,used≤0 跳过):兑换会员码 service.go:146、admin 直授 GrantToUser service.go:311、订阅订单履约 order.go:349 三处调用;降级/撤销刻意不调(quota.go:412-435)
- ceiling 来源:BillingConfig.DailyCeiling 纯函数,Free=FreeDailyTokens,Pro=×ProMultiplier,Max=×ProMultiplier×MaxMultiplier;任一≤0 → -1 不限(billing_model.go:73-93);默认值 Free=200000/Pro 倍率 5/Max 倍率 5(config.go:17-36),admin 经 PUT /admin/billing/config 可改(billing_handler.go:237-247),30s 内存缓存(config.go:39)
- EffectiveTier 单一真源:pro/max 且未过期→该档,否则 free(到期读时自动回落,无定时任务)(service.go:91-105)
- fail-open 兜底:Redis 不可用时退回进程内 fallbackCounter(按 day 字符串跨天清零的 map,每实例每用户当日累计,quota.go:128-155),warnQuotaDegraded 每分钟一条 WARN(quota.go:107-121);进程重启清零、多实例各算各的、恢复不回填

## designImplications
- 改 7 天滚动窗口的好消息:全部 12+3 个执法点与三个闸门函数签名都不用动——判定口径完全收敛在 vip 包内部两个函数:tokenWindowUsed(quota.go:192)与 DailyCeiling(billing_model.go:73)。把 tokenUsed/tokenBaseline 改成『过去 7 个日 key 求和』(MGET 7 key)、ceiling 换成 7 天上限(新配置列或 7×日上限),外部零改动;agent 侧 budget 帧(soft/hard 是剩余量语义)也天然兼容
- 必须动的点:① AddUsage 的 TTL 25h→至少 8×24h(quota.go:295),否则旧天 key 过期后窗口读不到;② tokenUsed/tokenBaseline 改 7 key 求和(读放大:每条 user_message 从 2 GET 变 14 key MGET,建议 pipeline 或短缓存);③ fallbackCounter 从单日 map 改 7 日环形桶(quota.go:128-155);④ resetNotNeeded/resetInternal/AddUsage 越线告警全部换 7 天口径(quota.go:354-410、303-320);⑤ billing_config 迁移加列(window_days 或 weekly_tokens 旋钮)+ admin BillingConfigPage 加编辑项 + PublicPlans/UsageCalendar 的 daily_ceiling 展示口径重定义
- 重置(花经费刷满)语义迁移是最大难点:现在 reset=『当日 base:=当日 used』,天然随 0 点作废。7 天窗口下推荐『豁免按日分桶』:保留 quota:base:<uid>:<day> 粒度,reset 改为『当日 base 桶 IncrBy 当前窗口用量』(而非 Set=used),窗口用量 = sum7(used) - sum7(base) clamp 0——豁免随该日滑出窗口自动失效,与 used 同构、改动最小、多次重置可叠加;ResetBaselineOnUpgrade 同样改 IncrBy。注意 reset 从 Set 改 IncrBy 后,幂等护栏(resetNotNeeded 双判 + 双层锁)必须保留,否则并发双扣从『无害重复 Set』变『真双倍豁免』
- 另一可选迁移:重置改为『额度包』模型(quota:extra:<uid>:<day>,判定 sum7(used) < ceiling7 + sum7(extra))——语义更直观(买的是增量而非清零),且与『7 天限额 + 模型目录化』的按需购买更契合,但前后端文案/UX 改动更大
- 『00:00 自动恢复』的产品语义在滚动窗口下消失(变成连续恢复:最旧一天滑出即释放该天用量)——所有前后端文案(quota.go:438-443、QuotaNotifier.tsx、account-assets-card.tsx、MobileAssetsCard.tsx、小程序侧)与 TokenStatus 字段命名(consumed_today→窗口统计+当日统计要拆两个字段)都要改;前端 membership.ts TokenStatus 本就缺 consumed_today 声明,重构时一并补齐
- 切换上线的冷启动问题:历史日 key 只有 25h TTL,切换瞬间过去 6 天数据已丢失→窗口只看得到当天,用户初期实际获得约 7 倍宽限。可接受(一次性放水)或从 MySQL llm_token_usage 回填 7 天(账本按行有 user_id/created_at/total_tokens,DailyUsageThisMonth 的 SQL 可直接复用,quota.go:475-485)
- 对『模型目录化+固定能力绑定』的约束:现额度是统一池、不分功能不分模型的 raw token 口径,AddUsage 签名只有 (userID, tokens)(quota.go:272),观察者接线在 bootstrap.go:388;若不同模型成本不同,需在此引入模型系数(加权 token)或按模型分池——分池会让 key 空间×N 且 12 个执法点都要带模型参数,加权是改动最小路径;ceiling 是 tier 纯函数,『用户选模型』若影响额度需在 billing_config 加 per-model 配置或模型绑 tier
- 透支带参数要重校准:OverdraftTokens = max(ceiling×15%, 20 万)(billing_model.go:104-113),ceiling 变 7 天口径后 15% 绝对值放大 7 倍、地板 20 万相对变小——透支带原意是『保证单轮 agent 能优雅收尾』,应保持单轮量级(建议改为固定量或基于日均而非 7 天总量)
- 多实例/故障语义继承:双层重置锁(进程内分片+Redis SETNX)、fail-open 契约(Redis 挂→有界放行+限流 WARN)、『先写 Redis 后扣费』的失败安全顺序都与窗口长度正交,7 天化时原样保留即可;但 fallbackCounter 的『进程重启清零』在 7 天窗口下敞口变大(重启丢 7 天而非 1 天记忆),权重上升需评估
- 测试与断言:billing_test.go:185 硬编码 key 字面、integration_test.go 全流程、bootstrap 五功能接线 panic 断言(bootstrap.go:375-385)——新增 feature 或改闸门时这些是回归护栏,7 天重构须同步更新
