## designImplications
- 绑定「便宜快」目录模型的最小改动点:service.go:153-162 fastModel() 的取值来源(现在读 agent_config.haiku_model)。meta(:1326)与 letter(:1428)共用这一个函数;若目录化后 meta/letter 要分别绑定不同能力档位,需把 fastModel 拆成按能力(capability key)查目录的两个调用点。下游 set_runtime_config→modelOverride 通道零改动。
- 硬约束:turnLoop 把 modelOverride 当裸 model id 用当前唯一活跃 provider 的凭据调用(set_runtime_config 的 ProviderID 恒为 nil,ws_serverside.go:160)。目录里的模型若跨 provider,必须扩展 set_runtime_config 携带 providerId + executor 侧 per-turn provider 解析,否则目录只能收录活跃 provider 可解析的 id——这是「模型目录化」对 agent 协议的核心冲击点。
- PushConfig 单 provider 4 槽架构(client.go:947-988)与 N 模型目录冲突:要么目录只作为 4 槽位取值来源(改动最小,槽位语义保留),要么重构 providerStore/推送协议支持多 provider 多模型(改动大)。
- 「用户选模型」与「固定能力绑定」是两类消费方:peerreview 全部 server-side、用户无模型入口(固定绑定);claw 等 WS 交互 feature 已支持 frame.tier 切换(ws.ts:86-87)。目录 schema 需要区分 user-selectable 与 capability-bound 两种暴露面,agent 协议对两者(modelId / tier)都已支持。
- 7 天限额影响:现在额度是「每日 token 统一池」(vip.CheckDailyQuota + AddUsage),账本 llm_token_usage 只有 feature=peer_review + model 维度,没有能力/阶段维度;预填识别与整场审稿共享同一 feature key 和同一池。若 7 天限额要按能力或模型档位细分,需在 llmusage.Call/Usage 加维度(reviewCallCtxWith 是注入点,service.go:1236)或为预填拆独立 feature key——同时注意 AdvanceStep 的闸门语义(检查在前、消耗后置,不预扣)。
- fastModel() 空值静默回退到主模型是成本暗坑:haiku_model 未配置时预填识别会烧主模型。目录化后建议改为强制解析 + 显式失败/告警,不再静默升档。
- meta 抽取有 fingerprint 缓存 + reset session 语义(advanceTo2 miss 时重建会话清全部 step_cache):换绑模型不影响缓存正确性(fingerprint 只含 assets_revision,不含模型 id)——但换模型后旧缓存仍命中旧模型的结果;若希望换模型强制重抽,fingerprint 需纳入模型标识。
- 评估「便宜快」模型时注意 meta 轮的真实负载:不是纯文本补全,而是带工具的 agent 轮(Bash 跑 pdftotext/pandoc + JSON 输出),模型需具备可靠 tool-use 与严格 JSON 能力;护栏已有(2 次 JSON 重试、5min ctx、单轮 5M token),但换弱模型可能提高重试率反而增本。
- 记账的 Provider 字段硬编码 'scholay-managed'(hooks.go:71):目录化后若引入多 provider,该字段及成本核算口径需同步改,否则账本无法区分上游。
