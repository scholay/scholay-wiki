## summary
「每日额度」体系的现状:后端真源是 backend/internal/vip,额度=统一 token 池(所有 AI 功能共用、不分功能不分模型),核心机制是「统计与限额分离」——Redis 日粒度 key `quota:tokens:<uid>:<YYYYMMDD>`(真实累计 used,AddUsage 单调累加,TTL 25h)+ `quota:base:<uid>:<日>`(窗口起点 base,重置/升级时抬到当前 used),闸门判定 = used-base < DailyCeiling(tier)(quota.go:1-20 头注释、96-99、190-224)。「每日重置」不是定时任务,而是**跨 0 点自然换 key = 自动满血**——这是整个日额度语义的根。上限 = free_daily_tokens × pro/max 倍率(billing_model.go:49,70-90,默认 200000,admin 经 /admin/billing/config 配)。超限走两条通路:HTTP/SSE 回业务码 6010(errcode.AgentQuotaExceeded,peerreview handler.go:421/448/863),WS 由 agentbridge 回 `error/quota_exceeded` 帧(ws.go:649-656);两者的用户文案同源 quotaExceededMessage(quota.go:438-443,「今日 AI 额度已用完…明日 00:00 自动恢复」)。前端信号已收口单一谓词 isQuotaSignal(quota-events.ts:15-22,http.ts BizCode.AgentQuotaExceeded 引用同常量;4020=PaymentRequired 是无关保留位),QuotaNotifier 单点消费弹「经费重置」弹窗。DTO 面:GET /user/billing/overview 回 Overview{tier,expires_at,token:{used,ceiling,percent,unlimited,consumed_today},credit,auto_reset,reset_cost}(quota.go:450-466,routes_user.go:126);GET /user/billing/usage-calendar 回 {days,daily_ceiling} 供当月热力图(billing_handler.go:75-87);POST /user/billing/reset 花 reset_cost 经费把 base 抬到 used=整窗口满血(quota.go:322-407);GET /billing/plans 公开 free_daily_tokens(billing_handler.go:208-226);admin GET /admin/users/:id/vip 复用同一 Overview。前端消费点:PC 会员页 AccountAssetsCard+ResetDialog、MembershipPage 热力图(levelOf 按 daily_ceiling 分档)、移动端 MobileAssetsCard、admin UserDetailDrawer TokenQuotaBar、QuotaNotifier/quota-toast(50%/80% 阈值提醒按 warnDay 每天去重)、PromoModal、Pricing/plan-card/subscribe-dialog 营销文案、claw/smart-search 的「未发送」blocked 轮(MessageTurn.tsx:209「今日 AI 额度已用完」、AssistantTurn.tsx:47「明日再来」),以及 frontend-user 之外的小程序(me 页+agent-socket)是同 API 第 4 个消费端。契约测试 tests/contract 锁定 6010/quota_exceeded 码值与 Overview 字段形状(zod passthrough 容忍加字段、删改字段会 fail)。所有 UI 均只依赖 used/ceiling/percent 的「窗口口径」,consumed_today 后端有输出但前端未消费。

## designImplications
- 错误码通路零改动:6010 / 'quota_exceeded' / isQuotaSignal / useAgentSocket 解卡 / blocked 轮持久化重发机制均不含窗口语义,改 7 天只动文案与 DTO;契约测试里码值断言可原样保留(contract.test.ts:47-70)
- Redis 结构是最大改造面:日 key+25h TTL+『跨0点换key=满血』整套机制要重设计——滚动 7 天需 MGET 最近 7 个日 key 求和且 TTL≥8 天(base 窗口起点机制、AddUsage 越线观测、RemainingBudget 透支带、ResetBaselineOnUpgrade 全部要换成 7 天窗口口径);若做 per-user 固定 7 天周期(锚点=订阅日/首用日),当前没有任何周期锚点存储,需新增持久化
- 『何时恢复』从常量(明日 00:00)变为动态:建议 Overview/TokenStatus 新增 window_reset_at(或 period_end)字段,否则 ~10 处「00:00 自动重置」文案(QuotaNotifier:121、assets-card:45/127/238、PricingPage:65、plan-card:28/108、后端 quotaExceededMessage)只能改成含糊表述;zod passthrough 容忍新增字段,不破契约
- reset(花经费刷满)经济语义巨变:每日模式一次重置最多买回 1 天额度,7 天模式=买回整周期剩余额度,reset_cost_credits 定价必须重估;quota.go:403 的 Consume ref_id 按天('20060102')的幂等语义也要按新窗口重审;这直接影响 QuotaNotifier/ResetDialog/MobileAssetsCard/小程序 4 处重置弹窗文案
- 50%/80% 阈值提醒的去重粒度(quota.store.ts warnDay=每天一次)在 7 天窗口下会整周期反复弹同级提醒——需改成按窗口期去重(前端要能拿到窗口标识,又回到 DTO 要透出 period 起点)或产品接受每日提醒
- usage-calendar 的 daily_ceiling 分档基准失效:7 天限额下无『每日上限』,热力图 levelOf(billing-panels.tsx:441-444)需换基准(如 ceiling/7 或绝对档);字段若改名牵动 membership.ts:144 + billing_handler.go:85-86 两侧
- free_daily_tokens 若改名(如 free_weekly_tokens)是 5 处同步:DB 列(需幂等迁移,考虑旧值×7 换算)+ billing_model.go + admin BillingConfigPage + PublicPlans 输出 + 前端两份 Plans 镜像(membership.ts:81 / landing/plans.ts:22);保留字段名只改语义则零迁移但埋坑,建议改名
- 文案单源优势:超限提示三端同源(quotaExceededMessage→WS 帧 message / HTTP 6010 message / peerreview),后端改一处、前端弹窗直接透传 errFrame.message——但前端还有大量硬编码『今日』文案(见 keyFacts 前端各条)需逐处改
- 最高优先级文案 bug:smart-search AssistantTurn.tsx:47『明日再来』在 7 天窗口下是错误承诺(可能要等 7 天),必须随窗口改造同步改;同理 QuotaNotifier 标题『今日 AI 额度已用完』
- 别漏第 4 个消费端小程序(me 页 + agent-socket quota toast);其 agent-socket.ts:180 用正则 /额度|quota/ 匹配 message 兜底,新文案只要保留『额度』二字仍命中
- 与『模型目录化+用户选模型』的交叉:当前额度是统一池不分功能不分模型(quota.go:199 注释明示),StandardHooks 的 CheckQuota 闭包签名只有 (ctx,userID)(agentbridge/hooks.go:96-99)、AddUsage 只有 (userID,tokens)——若 7 天限额要按模型/能力分池,这两个签名是必扩展的 seam;hooks.go:66 注释也预留了『per-user token 总额预算的实际扣减接在 recordAgentTokens』的设计缝
- 统计与限额分离的红利要保住:llm_token_usage MySQL 账本按 created_at 落库,天然支持任意窗口聚合(DailyUsageThisMonth 即模板),7 天窗口的核账/回填/热力图都可直接 SQL,不依赖 Redis 结构改造;consumed_today 前端未消费,改名/改口径无 UI 破坏,只需同步 contract fixture
