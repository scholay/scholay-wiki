## designImplications
- 4 槽位(main/haiku/sonnet/opus)是横贯三层的硬编码:DB 列(0001_baseline.sql)+ agentconfig.AgentConfig struct + client.ModelMapping(client.go:56-62)+ agent ProviderConfig.ModelSlots(providerStore.ts:10-15)+ resolveTier/listModels(models.ts)+ hub.validTier(hub.go:258)+ executor tier 白名单(ws.ts:87)+ 各 spec.DefaultTier + peerreview fastModel/mainModel。模型目录化 = 这些位置全部要动或全部要绕开;两处 tier 白名单是双份真源,漏改一处就静默失效
- 最低成本迁移路径:不动 executor 的 provider/槽位 schema,把目录完全放 backend——executor 已支持 per-connection modelOverride 且优先于 tier(turnLoop.ts:58),backend 只需在 hub(唯一咽喉)把「用户选的目录模型」解析成具体 modelId 后下发 set_runtime_config{modelId}(sendInitialTier 演化为 sendInitialModel)。PushConfig 仍只推 base_url+api_key+一个兜底 main;槽位语义退化为兜底
- 用户选择必须从前端 localStorage 迁到服务端:现状 per-session modelId 只存浏览器/微信 storage,换设备即丢、服务端无法做 entitlement 与按模型计费;目录化+固定能力绑定要求 agent_sessions 加 pinned_model(varchar(200),VARCHAR(16) 的 pinned_tier 装不下 model id)或新表,且 hub 重建时像 sendInitialTier 一样从 DB 重发——不能依赖前端 onOpen 重发(前端存储与服务端 entitlement 必然脑裂)
- 必须在 hub 加 entitlement 闸:当前用户可经 WS 发任意 modelId 直通上游(hub.go:844 无校验转发)。用户选模型后,set_runtime_config 转发前须校验「该用户/该会话有权用该模型」,否则 7 天限额与模型分级付费全部可被绕过;这也是唯一能同时覆盖 web/小程序的强制点
- 7 天限额改造集中在 vip/quota.go:day-key(yyyymmdd)方案要换成 7 天窗口(rolling 或固定周起点),连带 tokenBaseKey 重置语义、RemainingBudget/透支带盖章(SS#2)、fallbackCounter(进程内按日 rollover)、billing_handler 的 daily_ceiling 展示、前端重置 UX 全链路;若限额按模型分池,PreUserMessage/BudgetProvider 钩子签名需要带上会话当前模型(现在只有 userID+content),而 hub 是唯一同时知道「会话当前模型」与「本条消息」的地方——记账侧 llm_token_usage 已有 model 字段(message_complete usage.Model),分池统计有数据基础
- 固定能力绑定与现有架构正交:能力面(DisallowedTools/AddDirs/Skills/appendSystemPrompt)现按 feature 由 FeatureSpec 在 CreateSession/seed_history 注入且 executor「仅 meta 为空时回填」(ws.ts:101-118)——中途换模型不会换工具面。若能力随模型走,需要新增「模型切换时重下发能力面」的帧语义或干脆限制切模型只在新会话时刻生效(后者改动小得多,且与 pinned 语义一致)
- 重启一致性机制可整体沿用,但目录数据要走同一通道:现有保证 = backend SyncOnce + 60s resync + executor providers.json 轻持久化 + hub 重建时 seed+sendInitial* 重发。目录化后若模型解析留在 backend(推荐),executor 侧几乎无新状态;若目录要推到 executor,必须挂进 PushConfig+providers.json 同一自愈链,否则 executor recreate 后出现「目录旧/空」窗口
- 两个已知边界要在重构中显式处理:a) enabled=false 时完全不推送,但 executor 的 providers.json 残留旧 key 会继续生效——目录下线某模型需要显式撤销推送而非只停推;b) peerreview serverside 每次调用实时读 agent_config 取 model(无缓存),目录化后其 role→model 解析(fast/main)须保持读时最新语义,否则 admin 换模型后审稿仍用旧模型
- pinned_tier(0052)当前是半死代码:读路径(sendInitialTier)活着但写路径无前端触发,生产库里该列大概率全空——目录化迁移时可安全弃用/重定义该列语义,无存量数据包袱;但 claw 用户的 localStorage modelId 偏好是存量行为,切换到服务端 pinned 时需要一次性迁移或明确放弃
