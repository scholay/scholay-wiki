# window7-mechanics — verdict: needs-fixes

## [major] 重置豁免记在当天 base 桶 + 全局 clamp:旧 used 滑出后 base 残留,系统性多放水(单次付费重置最坏≈白送一整个窗口)
方案 §6.2 明确「base_today IncrBy 当前窗口用量,全局 clamp 不做 per-day clamp」。逐场景推演:同日多次重置、重置后当天继续消耗、跨 0 点后再重置——算术都对(每次 IncrBy 后 Σbase 恰好抬到 Σused,raw=0)。但「7 天后豁免滑出」场景出错:被豁免的 used 分布在过去 7 天,而豁免全记在今天的 base 桶;旧 used 桶比 base 桶早滑出窗口,期间 Σused−Σbase 变负、被 max(0,·) 吞掉,负残值等价于隐形免费额度,持续吸收新消耗直到 base 桶自己滑出。量化:Free 窗口 140 万,day1-6 烧 120 万、day7 烧 20 万后重置(base_day7=140 万);day8 起 day1-6 的 120 万逐日滑出而 base_day7 存活到 day13,期间最多 120 万新消耗被负值吸收不计额度——一次付费重置实际放水近 2 个窗口,同时把 §6.3 的 releases_tomorrow(最旧一天 used−base)也算成负数。方向恒为用户有利(base 永远在最新一天,used 只会更早滑出),不会误锁但直接掏空重置定价(§9-5 按 7× 价值重估的前提失效)。更优解:重置改为**逐日 Set base_d=used_d(pipeline 7 key,now 单次快照)**——豁免与用量同日同滑出、per-day raw 恒 ≥0(used 单调、base≤used)彻底无负值;并发双重置退回「无害重复 Set」语义,方案 §6.2 特意保留的 IncrBy 双扣护栏顾虑(quota.go:51-94 双层锁 + :360-388 resetNotNeeded 双判)整体降级回现状强度即可,不再是正确性关键。

## [major] base 桶 TTL 只字未提::395/:430 若仍 25h,付费重置的豁免次日静默蒸发
方案 §6.2 的 TTL 变更只写在 AddUsage 一条:「TTL 25h → 8×24h」(对应 quota.go:295 的 used 桶 Expire)。但 base 桶的两处写入——resetInternal 的 rdb.Set(ctx, tokenBaseKey…, 25*time.Hour)(quota.go:395)和 ResetBaselineOnUpgrade 的同款(quota.go:430)——方案没提。7 天窗口下 base 必须存活满 7 天才能持续抵扣;若沿用 25h,用户付经费重置后第 2 天 base key 过期,Σbase 骤降、窗口用量跳回满格,等于「重置只管一天」——付费功能静默失效且难排查(Redis 过期无日志)。必改:两处 base 写入 TTL 同步 8×24h(逐日 Set 方案下同理,7 个 base key 都要 ≥8d 或对齐各自 used key 剩余 TTL;超过 7 天的 key 反正不在 MGET 列表里,宁长勿短)。

## [major] ResetBaselineOnUpgrade「同改 IncrBy」不够:跳过条件用错口径 + 无锁无幂等,支付回调重试=双倍豁免
方案 §6.2 对升级满血只写了「ResetBaselineOnUpgrade 同改 IncrBy」,漏了两处:(1) quota.go:426-429 的跳过条件是 used := s.tokenUsed(今天单桶);used<=0 即 return。7 天口径下必须改判 tokenWindowUsed7<=0,否则「前几天烧了 130 万、今天还没用」的用户升级后拿不到满血(窗口仍满格),付费履约失效——这是方案要求逐点列出却漏掉的必改点。(2) 该函数不走 acquireResetLock、无任何幂等护栏(quota.go:418-435 全文无锁)。现状 Set base=used 语义下重复调用无害,所以没锁是对的;改 IncrBy 后,GrantToUser/Redeem/activateSubscription 的调用方重试(支付回调天然会重复投递)或与用户手动重置并发,就是真·双倍豁免。方案 §6.2 只给手动重置保留护栏,这里是护栏盲区。修法:要么把它并进 resetInternal 的锁+resetNotNeeded 路径,要么采纳 issue#1 的逐日 Set 方案(天然幂等,此问题消失)。

## [major] fallbackCounter「7 日环形化」一句话带不过:降级期无 base 概念,重置=扣钱不解锁,卡死窗口从 ≤1 天拉长到 7 天
方案 §6.2 只写「fallbackCounter:单日 map → 7 日环形桶」。对照代码有三个坑:(1) **降级期重置扣钱无效**:rdb==nil 时 tokenBaseline 返回 0(quota.go:181-183)、fallback 无豁免概念;resetInternal 里基线写入被 if rdb != nil 包住直接跳过(quota.go:392-399),但第 4 步照常扣经费(quota.go:401-408)→ 窗口用量不变 → 用户再点再扣。这是现存 bug,但现状跨 0 点自愈(fallback 单日 map 明早清零);改 7 日环后 fallback 持续累计过去 7 天,用户被卡+反复扣费最长 7 天。必改:rdb==nil 时 resetInternal 应直接返回友好错误不扣费,或给 fallback 加进程内豁免偏移。(2) **环形正确写法**:rollover(quota.go:136-141)现在是 day!=d 整体清零,环形化后不能只比相等——进程空转跨多天后必须按「桶日期距今 >6 天」逐桶淘汰,且 get 求和只加窗口内桶;建议 map[uint]map[string]int64(dayStr→tokens)+ 读时过滤,比定长数组下标环更不易错。(3) **Redis 恢复一致性**:降级期 fallback 里的用量永不回填 Redis,恢复后窗口低估持续 7 天(现状只 1 天);方案的「冷启动回填」思路(从 llm_token_usage 聚合)同样适用于恢复时刻,至少该在方案里声明接受与否。

## [minor] AddUsage 越线观测(:303-320)7 桶改法方案完全没写:base 仍读当天单桶会在重置/跨天后误报,prevWin/curWin 还需 clamp
quota.go:306-309 现算法 base := s.tokenBaseline(当天单桶),prevWin=(n−tokens)−base、curWin=n−base,与 DailyCeiling 比。7 天口径下这段方案未提,若不改:昨天重置过的用户(base 在昨天桶)今天 base 读 0,prevWin 直接用 n 比 WindowCeiling → 越线告警口径与闸门口径(Σ7)脱节,重蹈注释里「重置后误报」的覆辙。正确改法:IncrBy 拿到 n 后,同一 pipeline MGET 其余 6 个 used 桶 + 7 个 base 桶(13 key,now 与 IncrBy 同一快照),curWin=max(0, Σused6+n−Σbase7)、prevWin=max(0, Σused6+n−tokens−Σbase7),越线判 prevWin<WindowCeiling≤curWin;两值都必须 clamp,否则 issue#1 的负残值场景下 prevWin 为负、越线幅度算术失真。这也让每条扣减多一次 13-key MGET,方案风险表「MGET 14 key 读放大」的量估计要按每消息 2~3 次读修正(RemainingBudget/Check + AddUsage)。定 minor 因仅影响观测日志不影响扣减。

## [minor] MGET 与跨 0 点实现细节:14 key 必须单次 time.Now() 快照派生;MGET 缺失 key 是 nil 元素不是 redis.Nil;日切重置锁 key 失效
(1) 现代码每个读函数各自 time.Now()(quota.go:170/183/286/395)。7 桶化后若 used 列表和 base 列表分两次取 now,23:59:59.x→00:00:00.x 之间跨天会得到错位窗口(used 取 D-6..D、base 取 D-5..D+1),Σ 差出一整天;resetInternal 里「读 windowUsed」与「IncrBy base_today」跨 0 点则豁免落到新一天、而被豁免的 D-6 用量已滑出 → 又造负残值。必须每个操作开头取一次 now,14 个 key 和 IncrBy 目标全部从它派生。(2) go-redis 的 MGET 对不存在的 key 返回 []interface{} 里的 nil 元素而非 redis.Nil 错误,与现有 Get(...).Int64() 的 err→0 模式(quota.go:170-174)不同,解析要逐元素判 nil/字符串转 int64;方案写「MGET…pipeline」没提这层,实现时别照搬旧错误处理。(3) 重置锁 key 含日期(quota.go:59 quota:reset:<uid>:<day>):两请求跨 0 点各锁各天,锁不互斥;叠加 quota.go:73-76「3s 等不到也放行」的 best-effort 语义,IncrBy 方案下这两个缝都是真双倍豁免窗口(Set 方案下无害)——再次指向 issue#1 的逐日 Set 更优。存疑标注:跨日锁竞态需两请求恰跨 0 点且同用户并发重置,概率极低,故 minor。

## [minor] 透支带公式量级等价、「单轮收尾」原意保住,但「透支 00:00 自然归零」的既有承诺在滚动窗口下变为「占坑 7 天」,方案未声明
核对 billing_model.go:98-113:现值 = max(DailyCeiling×0.15, 200_000);方案 max(WindowCeiling×15%/7, 200_000) 因 WindowCeiling=7×daily 恒等于 daily×0.15,单轮收尾量级(SS#2:够 agent 一轮优雅收尾)完整保留,地板 200k 不变,公式本身无问题。但 billing_model.go:97 注释的既有语义「00:00 日窗口重置时透支自然归零(不结转)」在滚动窗口下不再成立:透支消耗计入当天 used 桶、要占窗口 7 天,深度透支的用户次日只释放最旧一天(可能很少),CheckDailyQuotaOverdraft(quota.go:264)会继续硬拦——从「明天满血」变「最长等 7 天逐日回血」。这不是算术错误而是行为/预期变化,方案 §6.2/§6.3 未提,注释、超限文案和 releases_tomorrow 展示都应覆盖「透支也随窗口滑出」这一点,否则用户侧观感是『透支后被锁更久』的隐性收紧。
