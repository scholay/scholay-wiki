# Research: 智能写作 (Scholay Prism) — Agent-Native 交付与优化调研

> 用 claw「成果交付」同一视角审视 Prism。Prism 交付物 = 文档本身(经 round/apply 进 IDE),非下载文件。

## 🎯 设计结论

- [10-synthesis-design.md](10-synthesis-design.md) — **优化设计**:Prism already nails the hardest part of agent-native delivery: a DB-source-of-truth, ephemeral-cwd, four-phase round/apply model with real-time diff streaming, a hardened two-sandbox security split (agent container egress-only + prism_tex network_none/shell-escape-off), per-project session isolation, anti-hallucination library-RAG cite, version chains, and quota/usage hooks. The round/apply model is the RIGHT path — keep it, do not move to Canvas-inline auto-apply or bolt file-actions. The optimization opportunity is fourfold: (1) sharpen the agent's self-model so it explicitly knows cwd is ephemeral, that nothing reaches the user until a round is applied, and that it should generate (not just edit); (2) unlock latent capability already in the code — per-hunk accept/reject (LatexDiffEditor has it, gated by displayOnly), multi-file round navigation (PendingRound already returns all files), agent-created new files (collectWorkspaceChanges deliberately skips them); (3) add a compile-fix auto-loop (extractCompileError already produces the line-numbered context; just wire the loop); (4) ship the deliverable surface and comingSoon items — LaTeX→docx via pandoc (already in agent container), project .zip, figure/data generation via sandboxed Bash+matplotlib in the agent container (claw already runs Bash safely there), venue templates + outline planner (venue_template_key column already exists). Every proposal maps to an existing primitive; net new infra is minimal.

## 📚 内部架构

- [01-internal-round-apply-delivery.md](01-internal-round-apply-delivery.md) — Prism's Core Delivery Model: Ephemeral Workspace Lifecycle & Multi-File Atomicity
  - Prism's architecture enforces a strict ephemeral workspace contract where the PostgreSQL database is the single source of truth, and the agent operates in an isolated, sessionized working directory (cwd) that never persists directly. The system implements a four-phase round-trip lifecycle (prepare → agent edits → collect changes → apply/reject) with real-time diff streaming and atomic batch persistence. The backend reads changes back from the agent's cwd using ReadWorkspaceFileFull, compares SHA256 hashes against DB state, and commits all changes in a single transaction via BatchAppendCurrentVersions, forming a version chain via BaseVersionID. Key gaps include lack of support for agent-created new files, no partial-accept per-hunk, fragile multi-file consistency under failure, and no explicit agent-native understanding of its ephemeral nature.
- [02-internal-agent-selfmodel-tools.md](02-internal-agent-selfmodel-tools.md) — Prism Agent Self-Model, Tool Policy & Capability Surface: Depths & Gaps
  - Prism's agent-native protocol is a constraint-based system prompt (140–152 lines in edit.go) injected once per session, telling the agent it serves a LaTeX editor in an ephemeral cwd. The tool policy is binary: Bash/Task/Agent/NotebookEdit are explicitly forbidden; Read/Write/Edit/MultiEdit are allowed within cwd-bound paths (enforced by decidePermission in ws.go). Three writing skills are loaded via --add-dir: prism-latex-format, prism-academic-writing, prism-discipline-conventions. Prism does NOT use agent's full capabilities—Bash is disabled (no plot/data generation), and Task subagents are forbidden. Compared to claw (which allows Bash), Prism's restriction is intentional and structural. Key gaps: the agent is never told "you serve a remote web user" or that disk is ephemeral; cross-file awareness is implicit (no explicit context); the skills lack integration with the "what not to do" negative examples that shift agent behavior; fallback file harvesting (mentioned in claw design) is absent.
- [04-internal-frontend-ux.md](04-internal-frontend-ux.md) — Prism Frontend UX: Agent Proposal Delivery & Acceptance Surfaces
  - Prism demonstrates mature agent-native delivery via two surfaces: (1) chat-driven round-trip with CodeMirror diff review gate, user approves via /round/apply; (2) inline-edit (Cmd+K) with quick-action chips, funnels to same round model. Backend materializes ephemeral cwd, agent edits via Read/Write/Edit, frontend collects post-completion and gates persistence. Key gaps: per-hunk accept/reject disabled (round-level only), optimistic preview may lag, multi-file edits bundled without per-file drill-down.

## 🌐 业界对照

- [05-industry-canvas-artifacts-docmode.md](05-industry-canvas-artifacts-docmode.md) — How AI Document Editors Deliver Agent-Authored Prose (Canvas, Artifacts, Notion AI, Gemini Docs, Copilot Word) + What OpenAI Prism Actually Is
  - OpenAI Prism is a real, shipping product (launched Jan 28, 2026): a free, browser-based, LaTeX-native research workspace with GPT-5.2 built in, evolved from OpenAI's acquisition of the Crixet LaTeX platform. The Scholay "智能写作" feature is therefore cloning a concrete competitor, not a hypothetical one. Prism's editing model is human-in-the-loop and document-centric: the model works inside the project context (structure, equations, refs), proposes changes that the user accepts via Keep/Undo per suggestion, with optional track-change-style visual diffs. Across the broader field, two delivery archetypes dominate: (1) regex/string-replacement edit operations against a live document (OpenAI Canvas's leaked `canmore` tool, Claude Artifacts' create/update/rewrite ops) where the model emits targeted patches and the host renders versions; and (2) native track-changes/suggestion-mode redlines (Microsoft Copilot in Word, Claude for Word, Notion suggested edits) where every AI edit lands as an accept/reject revision anchored to specific text. The single most adoptable artifact for Prism is Canvas's `canmore` system-prompt contract — explicit, quotable rules for when to create vs edit, and when to do a targeted patch vs a full rewrite.
- [06-industry-cursor-windsurf-cline.md](06-industry-cursor-windsurf-cline.md) — Change-Delivery UX in Agentic Code/Doc Editors: What Prism's Round/Apply Model Should Adopt
  - Across Cursor, Windsurf/Cascade, Cline/Roo, Zed AI, and GitHub Copilot, the dominant change-delivery pattern is a clear two-stage split: a frontier "planning" model decides WHAT to change and emits a compact edit representation (search/replace blocks or "lazy" snippets with `// ... existing code ...` markers), while a separate fast "apply" model or deterministic merger turns that into the final file. The review UX has converged on a small vocabulary — a multi-file change list, per-file and per-hunk Keep/Undo (accept/reject), inline red/green diffs with arrow navigation, an all-files accept/undo, and a checkpoint per agent turn that can roll back files and/or conversation independently. The single most contested decision is whether edits land on disk before acceptance: Cursor historically staged in-memory (its prized advantage), Windsurf/Cline write to disk and rely on a shadow-git checkpoint as the safety net. Per-hunk acceptance is universally demanded — users repeatedly say the agent gets 90% right and they need to reject the 1-2 wrong hunks without discarding the rest. For Prism, the highest-leverage adoptions are: true per-hunk accept/reject within a round (not just per-file), checkpoints decoupling file-rollback from conversation-rollback, an explicit multi-file round summary, and preserving the inline-edit (Cmd-K) vs agent-round duality. Prism's existing "agent emits patch, doesn't write to disk, watcher sandbox" already matches the staged-not-on-disk camp, which is the safer design these tools are converging back toward.
- [07-industry-overleaf-latex-typst.md](07-industry-overleaf-latex-typst.md) — LaTeX-Specific AI Writing Assistants: Delivery Models & What Prism Should Adopt
  - Surveyed how academic-writing/LaTeX AI assistants deliver value: Overleaf (Error Assist + Writefull/AI Assist), Typst/TypeTeX, SciSpace, Jenni AI, Paperpal, and AI-native LaTeX editors (OpenAI Prism, OpenPrism, LMMs-Lab Writer, Octree, TexMate). Two delivery paradigms dominate: (1) in-editor AI that proposes inline red/green diffs the user accepts/applies (Overleaf, OpenAI Prism, Octree's "autonomous edit with approval"), and (2) agent/tool pipelines that emit submission-ready artifacts — compiled PDF, exported DOCX with editable equations (OMML), and journal-formatted packages (SciSpace, Paperpal). The recurring deliverables academic users expect are: a compiling PDF (with an auto-fix loop so they never debug LaTeX), a Word/DOCX export for non-LaTeX co-authors and journals (the single biggest cross-format pain), automated BibTeX/citation management grounded in real sources, venue/journal templates with one-click reformat, generated figures/tables/equations as ready LaTeX, and track-changes/review for collaboration. Scholar Prism already nails the inline-diff round/apply model, compile-error extraction feeding the AI, library-RAG \cite, and PDF download; the highest-leverage gaps are an automatic compile-fix retry loop, venue templates, export-to-DOCX, fuller bib automation, figure/table/TikZ generation, and a review/comment layer.
- [08-industry-bolt-v0-export.md](08-industry-bolt-v0-export.md) — File-Emitting Generative Builders: How They Stream File Changes and Deliver Downloadable/Exportable Artifacts (bolt.new, v0, Lovable, Replit Agent) — and What Prism Should Adopt
  - The leading "prompt → app" builders (bolt.new, v0, Lovable, Replit Agent) share one delivery pattern: the LLM emits structured file actions that stream into a live, sandboxed preview, and the resulting project is the deliverable — exportable as a ZIP, pushable to GitHub (bi-directional sync), or one-click deployable to a live URL. bolt.new is the canonical reference for the file-action streaming convention: the model emits a single `<boltArtifact>` containing ordered `<boltAction type="file" filePath="...">` / `type="shell"` elements, parsed incrementally by a StreamingMessageParser and executed by an ActionRunner against an in-browser WebContainer that runs the dev server and serves the preview iframe. Lovable diverges by holding the project as an in-browser AST, computing minimal line diffs, and pushing them to ephemeral fly.io dev servers with Vite HMR. v0 and Replit add bi-directional GitHub sync (auto-branch + auto-commit, never push to main) and self-healing build loops (run → read errors → fix → checkpoint). For Prism, whose true deliverable is a compiled PDF plus the .tex source, the highest-leverage adoptions are: (1) a project-ZIP export route (sources + latest PDF + bibliography), (2) a prominent one-click "Download PDF" and "Download project" surface, (3) optional GitHub/Overleaf export, and (4) surfacing the existing compile-error feedback loop as a visible build status. Prism already has the compile→PDF→error-extraction loop in place; the missing piece is the export/download deliverable surface.
- [09-industry-ai-figures-data-export.md](09-industry-ai-figures-data-export.md) — Agent-Native Figure/Table/Document Delivery: Industry Patterns and What Prism Should Adopt
  - AI writing/analysis tools deliver figures and exported documents through a small set of repeatable patterns: an agent writes Python (matplotlib/pandas) into a sandboxed code-execution environment, the runtime returns the chart as base64 PNG (or a file in a known output directory), the result is embedded into the conversation/document, and the document is exported via a pandoc/typst/LaTeX pipeline. The security model is consistent across vendors: untrusted model-generated code runs in an isolated, network-disabled, ephemeral sandbox (gVisor/Firecracker), with file I/O over an explicit upload/download channel. Prism's blocker is that its agent disallows Bash, so it cannot run python/matplotlib to generate figures, even though its sibling feature claw already runs Bash safely in the same hardened, egress-only agent container and already implements an OpenAI-style "out/ artifact directory" download mechanism. Prism also has a network-isolated LaTeX compile sandbox (prism_tex) that triple-locks shell-escape OFF, so pythontex/minted in-document plotting is impossible there. The recommended path: generate figures with python/matplotlib inside the agent container (which is the correct, hardened place to run code), emit PDF/PNG figures into the project, \includegraphics them, and add a pandoc-based LaTeX→docx and a PDF download as the exported deliverables — reusing claw's artifact pattern and not weakening the compile sandbox. This keeps code execution and TeX compilation in separate hardened sandboxes, matching the industry split.
