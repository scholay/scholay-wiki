# 小程序化（微信 + 抖音）可行性与路线决策报告

> 调研日期 2026-06-26 · 方法：7 个并行调查 agent（代码现状 / 微信合规 / 抖音合规 / 技术路径 / web-view 套壳 / WebSocket 实时 / AIGC 合规）+ 8 条高风险结论对抗式 Web 核实（官方来源）。
> 时效声明见文末第 5 节；凡"硬门槛"以国家网信办、工信部、各省通管局及微信/抖音开放平台**后台最新口径**为准。

## 1. 执行摘要 + 一句话推荐

**不能"直接兼容"。现有 React 19 Web SPA 的整个视图层在小程序里 0% 可运行，必须"复用后端 + 共享类型契约 + 前端另起小程序工程"。最大卡点不是技术，而是 AIGC 合规——当前用境外 Anthropic/Claude 给境内 C 端做 AI 问答，这在微信/抖音上线几乎不可能过审，优先级高于一切技术与备案文书。推荐路线：先切境内已备案大模型 + 办备案（关键路径，最先启动），技术上走"web-view 套现有 /m H5 + Taro 重写少数轻交互原生页"的混合方案，首版裁掉智能写作 / PDF 富预览 / AI 审稿。**

三个层面的定论：

- **能不能直接兼容**：❌ 不能。小程序运行时无 `DOM`/`window`/`document`，Radix/framer/PDF/CodeMirror/recharts/mermaid/katex 全部依赖真实 DOM，无法运行。
- **该走哪条路**：混合方案——web-view 复用 H5 承载重交互（文献浏览/AI 对话/写作），Taro 做登录/搜索/列表等轻交互原生页。**前提：必须企业主体**（个人主体不能用 web-view、不能开支付、不能申请 AI 类目，三重出局）。
- **最大卡点**：🔴 **AIGC 合规中的"模型来源"**。境外模型无法在网信办备案，平台 AI 类目审核要算法备案号，给不出 → 直接驳回，已有批量下架/处罚先例。

**关键判断：这是一个"合规决定能否做、技术决定怎么做"的项目。如果不愿意把上游模型切成境内已备案模型，则小程序化在合规上不成立，技术评估无意义。**

## 2. 第一部分 · 申请与合规

### 2.0 决定性前置卡点（🔴 最高优先级）

⚠️ **境外/未备案大模型 = 死结**。《生成式AI暂行办法》明确覆盖"向境内公众提供生成内容的服务"，本项目 100% 落入监管。Anthropic/Claude 等境外模型**无法在网信办备案**，任何"自有后端转发/中转/套壳"客观上都办不下来《暂行办法》要求的备案或登记。已有真实的批量下架与处罚先例（微信/抖音/苹果商店下架套壳 AI 应用；监管要求"严禁以任何形式使用境外大模型"）。

平台 AI 类目审核（微信"深度合成-AI问答"、抖音 AIGC 类目）硬性核验**互联网信息服务算法备案号**，上游给不出 → 类目审核环节即被打回。

> **唯一可行解**：后端上游切换为**境内已备案大模型官方 API**（通义千问/文心/豆包/智谱/DeepSeek 等已备案模型），用其备案号 + 与厂商签合作协议过审。境外 Claude 只能留给非小程序端（Web/App）。

### 2.1 主体类型（两端均：个人出局）

⚠️ **必须企业主体（或个体工商户），个人主体三重出局**：

| 能力 | 个人主体 | 企业/个体工商户 |
|---|---|---|
| 微信支付 / 收会员费 | ❌ 不能开通 | ✅ |
| web-view 嵌外部 H5 | ❌ 无业务域名配置入口 | ✅ |
| AI 问答/深度合成类目 | ❌ 未开放 | ✅ |

> 核实修正：微信支付准确口径是"个体工商户/企业/事业单位/政府机关/社会组织等**经营主体**"，**个体工商户（有营业执照的个人经营者）也可以**，纯自然人个人主体不行。抖音侧个人主体小程序接入实务上已**暂停**（仅小游戏/小玩法）。结论：直接用企业主体，尤其涉及与大模型厂商签算法备案合作协议时企业主体更顺。

### 2.2 服务类目（避开前置审批雷区）

一个小程序最多 5 个类目，每月最多改 5 次。建议组合：

| 业务 | 推荐类目 | 资质 |
|---|---|---|
| 学术/文献检索 | **工具 > 信息查询** / 科研效率工具 | 弱化"资讯/新闻"，避免触发《互联网新闻信息服务许可证》 |
| AI 助手/搜索/写作 | **深度合成 > AI 问答 / AI 创作** | ⚠️ 强制算法备案 + 合作协议 |
| AI 审稿（学术教育属性） | 谨慎选教育类 | ⚠️ 微信教育类目部分需前置审批；抖音教育类需"邀约开放" |

⚠️ **避坑**：不要选"新闻资讯"（需新闻许可证）、不要轻选"教育培训"（需办学许可/前置审批）。学术论文聚合**极易被判为需资质的资讯/出版**——务必弱化资讯表述、只做"元数据 + 跳转官方来源"，不托管全文 PDF。

### 2.3 备案（ICP 强制 + 软著非强制）

| 项 | 是否强制 | 周期 | 口径 |
|---|---|---|---|
| **ICP/APP 备案** | ⚠️ 强制 | 1–22 工作日（实务 1–3 周） | 微信自 **2023-09-01** 起新小程序须备案后才可上架；由**平台代为**向省级通管局提交，非直接向工信部申报 |
| 软件著作权 | 非强制（工具类） | 30–60 天 | 仅小游戏强制；建议并行办，**非上线阻塞项** |
| 增值电信经营许可证（ICP 证） | 视情可能触发 | 1–3 月 | 有会员付费=经营性互联网服务，**可能被要求**（注册资本≥100万），潜在隐性成本，预留预算 |

### 2.4 内容安全（强制接入 + 双向过滤）

⚠️ **强制**。凡有 UGC 或 AI 输出内容，平台要求接入内容安全 API（微信 `security.msgSecCheck` / 抖音内容安全检测接口），**提审时要录屏演示接口调用成功**。本场景全中招：搜索词、AI 对话输入、AI 输出文本。

⚠️ 此外《安全基本要求》要求**输入 + 输出双向过滤** + 关键词库/测试题库 + 违规处置（连续 3 次或一天累计 5 次违规须暂停服务）。**本项目目前只有配额/限流，没有统一内容安全过滤层 → 这是必须新增的功能性硬开发，不只是文书。**

### 2.5 AIGC 备案与标识

| 义务 | 性质 | 落地动作 |
|---|---|---|
| 算法备案（生成合成类-深度合成） | ⚠️ 硬门槛 | 平台 AI 类目门票；周期 1–2 月（实操可达 3–4 月） |
| 大模型登记（调已备案 API，本项目属此类） | ⚠️ 硬门槛 | 周期 1–3 月（自研/微调走"大模型备案"则 3–6 月） |
| 安全评估（舆论属性） | ⚠️ 硬门槛 | C 端 AI 问答几乎必然被认定，并入算法备案流程 |
| AI 生成内容标识 | ⚠️ 强制（2025-09-01 起） | **显式**：回答气泡/卡片加"AI生成"角标；**隐式**：导出文件（PDF/LaTeX/审稿报告）元数据写入标识 |

> 核实修正：①平台审核硬门槛锚定**算法备案号**，不是"算法备案号 或 大模型备案号"二选一——算法备案与大模型备案/登记是两件不可互替的事。②标识：**显式标识 + 元数据隐式标识为强制，数字水印类为"鼓励"非强制**。③网信办 2025-11 已集中查处未标识 App，是真实执法红线。

### 2.6 支付资质（会员收款）

⚠️ **H5 跳转支付在小程序内完全无效**，必须改造：

- **微信**：会员付费走原生 `wx.requestPayment`（后端需新增 JSAPI 下单端点）。**支付宝在微信内被屏蔽，不可用。** iOS 端：2025-11 苹果"小程序合作伙伴计划"破冰，微信已官宣 iOS 虚拟支付支持，**苹果抽成 15%**（设计会员价要算进"苹果税"）。
- **抖音**：必须 `tt.pay`。⚠️ **抖音 iOS 虚拟支付历史上被封死**（会员/AI 额度属虚拟商品），且**不得引导外跳付费**（App/H5/二维码/网页全禁）。截至研究时点抖音官方文档仍写"iOS 不支持虚拟支付"。**结论：抖音不宜作为会员变现主战场，iOS 端会员只能"别处开通、端内仅展示已开通状态"。**

## 3. 第二部分 · 技术改造

### 3.1 为什么不能直接兼容（React Web ≠ 小程序运行时）

1. **小程序没有 DOM/window/document**。逻辑层跑在 JsCore（无 BOM/DOM），渲染层是独立线程的 WXML/WXSS。Taro 用自研 React reconciler（**不是 ReactDOM，也不是现在的 React 19**），uni-app 把 Vue 模板编译成 WXML。任何直接操作 DOM、读 `window`、`getBoundingClientRect`、Canvas2D DOM、Web Worker 的库**全部跑不了**。
2. **网络层必须换**：`axios`（基于 XHR/fetch）跑不了 → `wx.request`/`tt.request`；原生 `new WebSocket()` → `wx.connectSocket`；`fetch + ReadableStream` 的 SSE **小程序不支持**。所有请求域名要进白名单 + 强制 HTTPS/WSS、不能用 IP/端口。
3. **web-view 只有企业主体能用**（见 2.1）。

### 3.2 可复用 vs 必须重写

**✅ 可复用（与视图层解耦）：**
- 后端 REST API（零改动，仅配域名白名单）+ JWT Bearer + ws-ticket 鉴权模型
- TS 类型契约（`shared/api/*`）、业务错误码表（`BizCode`）、zod schema
- 领域纯函数（`minicod-papers.ts`、`citation.ts`、`agent-history/stream/prefix.ts` 等）
- TanStack Query 查询逻辑（换底层 http adapter 即可）、zustand store 的纯逻辑（剥离 `window/localStorage` → `wx.getStorageSync`）

**❌ 必须重写（数百个 .tsx 视图层 = 0% 直接复用）：**

| 依赖 | 小程序里的处置 |
|---|---|
| 所有 `@radix-ui/*` + shadcn ui | 全砍，改 NutUI-React / Taro UI 重写弹层/下拉/Dialog |
| **react-pdf + pdfjs-dist** | 原生不可用 → `wx.openDocument` 调系统阅读器，或 web-view 内 H5；**富交互预览做不了** |
| **CodeMirror（Prism 写作）** | 原生不可用（纯 DOM 编辑器）→ **智能写作首版砍掉，或仅 web-view 承载** |
| **katex** | `rich-text`/`mp-html` 受限渲染，复杂公式塌 → 服务端转图 |
| **mermaid** | 原生不可用 → 服务端渲染成图片下发，或 web-view |
| **recharts** | 无 SVG → 换 `ec-canvas`/`@antv/f2` 重写 |
| **react-markdown** | 换 `mp-html` 类小程序库 |
| **framer-motion** | 全砍 → `wx.createAnimation`/WXSS，能力大幅缩水 |
| **Tailwind v4** | 降级 `weapp-tailwindcss`（v4 支持滞后、坑多）+ rpx |
| **react-router v7** | 换小程序页面栈路由，`<Link>`/`useNavigate`/`loader` 全失效 |

### 3.3 三处硬改造点的处置

- **WebSocket（中等改造，可平移）**：现有"先 POST 拿一次性 `ws_token`，再 `?ws_token=` 升级 wss"模型**几乎零改造，且恰好是小程序里最稳的姿势**（白名单只校验 host，query 不参与；自定义 header 在真机不可靠，token 放 query 反而更稳）。核心适配：浏览器 `WebSocket` → `wx.connectSocket` 适配层。⚠️ **最大风险：切后台/熄屏 5s 必断**——长 AI 回答期间用户切后台即断流，必须 `onHide`→close、`onShow`→重连 + **强制断点续流**（本项目已有 `resync`/`replayBuf`/心跳，直接复用）。建议 ws_token TTL 放宽到 60s。
- **SSE 流式**：小程序不支持 `EventSource` 和 `ReadableStream`。微信有 `enableChunked` chunked 替代但**抖音根本没有**，且单向、真机坑多 → **不要改 chunked，统一用 WebSocket**（双向、两端统一、交互最完整）。
- **登录（中等改造）**：`localStorage` → `wx.setStorageSync`；删 cookie/iframe 共享逻辑、跨 tab `storage` 事件。**核心机会：改静默登录**（`wx.login`→code→后端换 openid/unionid，后端需新增小程序专属 code2session 端点）。
- **支付**：见 2.6，前后端都要新增小程序专属实现；web-view 内 H5 拿不到 `wx.requestPayment`，须 `wx.miniProgram.navigateTo` 跳原生页支付（注意 postMessage 只在 back/destroy/share 时回传，非实时）。

### 3.4 路径决策矩阵

| 维度 | A: web-view 套 H5 | B: Taro(React) | C: uni-app(Vue) | D: 原生双端 |
|---|---|---|---|---|
| 后端复用 | 100% | 100% | 100% | 100% |
| 前端代码复用 | ~100%（就是 /m） | 逻辑中、视图低 | 低（React→Vue） | 0 |
| 首期工作量 | **0.5–1 人月** | 4–8 人月 | 5–9 人月 | 8–16+ 人月 |
| 双端维护 | **极低** | 中（80%共用） | 中 | 最高 |
| PDF/CodeMirror/katex/mermaid | **原样可用** | 不可用/降级 | 不可用/降级 | 不可用/降级 |
| 原生体验/性能 | 弱（套壳感） | 中-高 | 中-高 | **最高** |
| 审核风险 | **高**（尤其抖音查套壳） | 低 | 低 | 低 |
| 主体门槛 | **必须企业** | 企业(AI类目仍需) | 同 | 同 |
| 与现有 React 栈契合 | 完美 | **好** | 差 | 差 |
| 推荐度 | 起步首选 | 核心页补充 | 不推荐 | 不推荐 |

**为什么不选 C/D**：C（uni-app）是 Vue 栈，本项目 React 重仓 → 多养一套技术栈、人和代码零共享，复用账算不过来。D（原生双端）工作量/维护最高，只有深度绑定某端独有能力（抖音电商/直播）才值得，对学术工具产品是过度投入。

## 4. 推荐路线图

### 阶段 0：合规启动（第 0–8 周，与开发并行，关键路径）
- 🔴 **产出**：注册企业主体小程序；**后端上游切境内已备案大模型**并签合作协议拿备案号；启动算法备案 + 大模型登记；ICP 备案；办软著（非阻塞）。
- **这是整个项目的瓶颈，必须最先启动。** 模型不切，后面全部白做。

### 阶段 1：技术选型 + 登录/网络底座（第 2–4 周）
- **产出**：确定混合方案；搭 Taro 原生壳；实现静默登录（code2session 新端点）；网络 adapter（axios→Taro.request）；WS 适配层（connectSocket + 切后台重连 + resync）；生产域名进白名单。

### 阶段 2：MVP（第 4–8 周，功能裁剪）
- **首版裁掉/降级**：
  - ❌ **智能写作（Prism/CodeMirror）** — 小程序原生承载不了，首版砍掉或仅 web-view。
  - ❌ **PDF 富交互预览** — 降级为 `wx.openDocument` 调系统阅读器。
  - ❌ **AI 审稿** — 重交互 + 文件导出 + 合规复杂，首版砍掉。
  - ⚠️ **katex/mermaid** — 服务端转图或暂不支持复杂公式/图表。
- **首版保留（web-view 复用 /m H5）**：文献检索浏览、AI 智能搜索对话、AI 助手对话（wss 流式可平移）。
- **Taro 原生页**：登录、搜索入口、论文列表、文献集、个人中心、会员（原生支付）。
- **必做合规开发**：内容安全双向过滤层 + AI 生成显式/隐式标识。

### 阶段 3：双端发布（第 6–10 周起）
- **产出**：微信先行（合规路径更清晰、iOS 支付已通）；抖音后置（iOS 虚拟支付受限，会员仅展示已开通状态）。提交类目审核（带备案号）+ 版本审核（录屏内容安全接口）。
- **微信优先于抖音**：抖音对套壳/资讯/虚拟支付审核更严，且需配套做短视频内容才有流量。
