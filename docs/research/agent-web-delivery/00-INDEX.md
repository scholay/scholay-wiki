# Research: Agent-Native Web Delivery of Generated Content

> **目标问题**:让 claw(及其它 feature)的 agent **从架构层面自己理解**——
> "我最终是通过 Web 在服务用户,本地文件(读/写)都是临时草稿,最终内容必须主动交付出去",
> 而不是靠后端硬性的文件传递规则(硬规则只作兜底)。

这个目录统筹该问题的全部调研与设计产出。

## 🎯 设计结论(先读这个)

- [11-synthesis-design.md](11-synthesis-design.md) — **综合设计文档**:Scholar's claw/smart-search/prism agents run in a per-session isolated cwd but have NO architectural notion that they serve a remote web user and that their disk is ephemeral scratch that never reaches the user by itself. The fix is agent-native: give the agent (a) a correct self-model injected at the agentbridge first-message prefix (Layer 3) — "you serve a user over the web, your cwd is private scratch, nothing on disk reaches the user unless you deliver it" — and (b) a single first-class affordance, a `deliver_artifact(path, title, description)` tool whose very description teaches the negative fact the agent cannot infer (files on disk are invisible to the user). The backend intercepts the deliver tool_use_complete frame in the existing agent2front pipe (the same seam that already auto-approves permission_request and harvests message_complete usage), validates path within the session cwd, harvests the bytes via GetWorkspaceFile/ReadWorkspaceFileFull, persists to MinIO, and emits a typed `artifact` frame the frontend folds into a download/preview card. The hard backend rule (list the output dir after each turn and harvest unannounced files) is kept ONLY as a secondary safety net for when the agent forgets to call deliver. This borrows Claude Artifacts' signaling+rubric, smolagents' final_answer "the description IS the teaching" mechanism, code-interpreter's known-output-dir convention, MCP resource field shapes for the wire, and Prism's agentNativeProtocol as the in-code prompt template — all mapped onto existing primitives (buildInjectionPrefix, decidePermission/pathWithin, OnMessageComplete, GetWorkspaceFile, claw file proxy, agent readTree).

## 📚 内部架构调研

- [01-internal-agent-self-understanding.md](01-internal-agent-self-understanding.md) — Scholar Agent Role/Context Understanding: Multi-Layer Prompt Injection Architecture
  - Scholar's agent (scholar_agent daemon) understands its role through a sophisticated 4-layer prompt injection system: (1) **base CC system prompt** (baked into Claude Code itself, rarely exposed), (2) **output style** (agent/data/claude/output-styles/paper-reviewer.md — role persona + behavior rules), (3) **agentbridge prefix** (backend/internal/agentbridge/ws.go buildInjectionPrefix — "[AGENT BRIDGE — STRICT RULES]" wrapper injected on first user message), (4) **per-feature prompts** (backend/internal/prompts/*.go — feature-specific system prompts like ClawSystemPrompt). Critically, **the agent currently has NO notion it serves a remote web user or that local files are ephemeral** — Claw and SmartSearch prompts assume local file system persistence and make no distinction between local vs. web delivery. For web-delivery self-understanding, the injection point should be agentbridge prefix (layer 3), not output style, because prefix is applied dynamically per-session and is the only layer aware of the session's hosting context.
- [02-internal-file-io-workspace.md](02-internal-file-io-workspace.md) — Scholar Agent File I/O Lifecycle: Complete Flow Analysis
  - The Scholar system implements a "Plan B" file architecture where the backend pushes raw files into the agent's session-isolated work directory (~/sessions/<sessionId>/), and the agent's native file tools (Read/Write/Edit/etc.) operate within this sandbox. Content egress flows through three channels: direct preview reading (text ≤1MB, images as dataUrl base64), full reads with full=1 bypass for large text, and GET /claw/session/file for image proxying. Permission gating happens bidirectionally: backend validates session ownership via OwnsSession, agent sandbox via pathWithin checks in agentbridge WS handler. The agent itself lacks awareness of file endpoints but gains implicit capability through permissionAllowed rules in the permission_response pipeline.
- [03-internal-prism-precedent.md](03-internal-prism-precedent.md) — Prism: Agent-Native Content Delivery Architecture — Reusable Patterns for Web Delivery
  - Prism (Scholay's intelligent writing assistant) demonstrates the most mature "agent produces content that reaches a web user" pattern in Scholar. Its core insight is the ephemeral workspace contract: the database is the single source of truth; the agent operates in an isolated, sessionized working directory that never persists directly; the backend reads changes back and applies them atomically to the database. This decouples agent execution from data safety and enables user-facing diff/apply/reject gates. The system uses a round-trip lifecycle (prepare → cwd materialization → agent edits via native Read/Write/Edit → pending collection → user approve/reject → atomic batch apply to DB), supported by real-time diff streaming via CodeMirror merge view and WebSocket-based agent-native protocol messaging.
- [04-internal-tool-output-protocol.md](04-internal-tool-output-protocol.md) — Scholar Agent Protocol for Artifact Delivery: WS Events, Tool Registration & Permission Interception Template
  - This research maps the Scholar agent's WebSocket protocol (ServerMessage types), tool architecture, and the backend permission-request interception pattern to identify where an agent-native "deliver/present artifact" signal could integrate. The protocol defines 19 ServerMessage types with content_delta (streaming), tool_use_complete (structured tool invocation), and message_complete (usage metadata). Tools register via dynamic imports in tools.ts and expose input schemas. The backend intercepts permission_request frames mid-stream, auto-approves or denies based on tool+path validation, and replies with permission_response — this is the template for custom delivery signals. Four design options are available: (a) a built-in Publish tool following tool registry patterns, (b) an MCP resource/capability via preinstalled-mcp.json, (c) a structured output convention (JSON in tool_result), and (d) tool_use interception (high coupling). Options (a) and (b) are production-ready; (c) requires agent cooperation; (d) is fragile.

## 🌐 开源 / 业界调研

- [05-oss-claude-artifacts-and-canvas.md](05-oss-claude-artifacts-and-canvas.md) — How Claude Artifacts & OpenAI Canvas Instruct the Model to Emit a Web-Surfaced, Self-Contained Deliverable
  - Both products solve the same problem — "model produces a standalone work product that the web UI lifts out of the chat into a side panel" — but with two different signaling mechanisms. Claude Artifacts uses an INLINE XML tag convention: the model wraps the deliverable in `<antArtifact identifier=... type=... title=...>` (preceded by a one-sentence `<antThinking>` self-justification), and the web front-end stream-parses these tags out of the assistant message, captures the content, and renders it in a sandboxed iframe panel, leaving a clickable card in chat. OpenAI Canvas instead uses a TOOL/FUNCTION mechanism: a `canmore` namespace with `create_textdoc` / `update_textdoc` / `comment_textdoc` functions injected into the system prompt; the model "opens the canvas" by calling the function. In BOTH cases the system prompt is the thing that teaches the model the web-serving context and a near-identical decision rule: create the deliverable only for substantial (>15 / >10 lines), self-contained, reusable, user-owned content, and otherwise stay inline — defaulting to NOT creating one when unsure. Versioning is by stable identity: Claude reuses the kebab-case `identifier` across the artifact lifecycle (same id = update, new id = new artifact); Canvas edits "the most recent document" and rewrites the whole body via a `.*` regex pattern. Directly adoptable for our claw agent: an explicit signaling envelope + a system-prompt-encoded "is-this-a-deliverable?" rubric + a stable id for create-vs-update, all of which our agentbridge could surface as deliverable cards.
- [06-oss-code-interpreter-sandbox.md](06-oss-code-interpreter-sandbox.md) — Surfacing Sandbox-Generated Files to Web Users: The Code Interpreter Pattern (OpenAI, E2B, Daytona, Jupyter Runners)
  - Across OpenAI Code Interpreter (Assistants + Responses APIs), E2B, Daytona, and Jupyter-kernel agent runners (AutoGen, Qwen-Agent), the same three-stage pattern recurs for getting files out of an ephemeral sandbox: (1) the model writes files into a known output directory (canonically /mnt/data on OpenAI, /home/user on E2B, the sandbox home on Daytona); (2) files reach the user via one of two channels — inline rich results captured from the Jupyter kernel's display protocol (base64 PNG, returned automatically), or out-of-band file references the platform resolves by either parsing model-emitted annotations (file_path / container_file_citation) OR by directly listing the output directory and downloading every file; (3) the platform turns these into download links / inline previews and (crucially) persists them off-box because the container is ephemeral (OpenAI containers expire after 20 min idle; ChatGPT sessions ~60 min). The model is told where to save files via a one-line system-prompt convention ("The drive at '/mnt/data' can be used to save and persist user files"), but practitioners found annotation-based surfacing unreliable and converged on directly listing the container's file directory as the robust contract. Our claw agent already implements the per-file read half (GetWorkspaceFile by known path) but is missing the "list output dir" half — adding a workspace directory-listing endpoint would let us adopt the same list-then-present contract without relying on the model to announce filenames.
- [07-oss-openhands-swe-agents.md](07-oss-openhands-swe-agents.md) — How Coding/Workspace Agents Surface Work and Model Their Own Environment (OpenHands, SWE-agent, aider, Cline/Roo, Devin)
  - Coding agents split sharply into two layers: (1) the agent-facing interface, which is deliberately NOT the human view, and (2) the human-facing surfacing of the agent's work. SWE-agent's ACI paper is the clearest articulation that "LM agents are a new category of end user" needing a non-human interface — concise feedback, a 100-line file viewer, linting guardrails — and it explicitly argues human IDEs are unsuitable for agents. None of the five systems put live "the user is watching your screen" framing in the agent prompt; instead, human-awareness is encoded at handoff boundaries: aider auto-commits every edit as a Conventional-Commit with "(aider)" attribution (commits ARE the deliverable), Cline writes every tool step into a shadow git repo so the user can diff/restore checkpoints, OpenHands streams typed Action/Observation events to a React SPA and requires an explicit "AI disclosure" note when posting content humans will read, and Devin exposes a 4-tab workspace (Shell/Browser/Editor/Planner) with a "Following" mode and delivers via PRs. For a chat-style research assistant, the adoptable core is: model your own output as a deliverable that will be surfaced/handed off to a human (commit/cite/disclose), keep the agent's internal interface concise and machine-optimized, and surface artifacts as diffable/restorable units rather than a live mirror.
- [08-oss-final-answer-tool-frameworks.md](08-oss-final-answer-tool-frameworks.md) — The "final_answer / deliver" Tool Pattern Across Agent Frameworks — and a Minimal deliver_artifact() for Claw
  - Across agent frameworks there is a consistent pattern: the agent must EXPLICITLY hand back its result through a dedicated tool call rather than leave output implicit in chat text or on disk. HuggingFace smolagents makes this most literal — a `FinalAnswerTool` (name `final_answer`, input `answer: any`) whose only job is to return its argument; the agent loop runs until that tool is called, and the system prompt explicitly teaches "In the end you have to return a final answer using the `final_answer` tool." The same idea appears as ReAct's `Finish[answer]` action, AutoGPT's `finish(reason, suggested_next_task)` command, CrewAI's `output_pydantic`/`output_json`/`output_file` task contract + `TaskOutput`, and LangGraph's `Command(update=, goto=)` for state-update-plus-handoff. The crucial mechanism is that the TOOL'S DESCRIPTION/SCHEMA is what teaches the model the contract — and several frameworks let final_answer carry rich payloads (smolagents `AgentImage`/`AgentAudio`/`AgentText`, CrewAI files/Pydantic). For Claw, the cleanest minimal adoption is a `deliver_artifact(path, title, description)` tool whose very existence + docstring makes the agent self-aware that local files are NOT auto-delivered and must be explicitly handed off.
- [09-oss-webapp-and-deliverable-generators.md](09-oss-webapp-and-deliverable-generators.md) — How web-deliverable agents (bolt.new, v0, Lovable, Replit Agent, Manus) frame "building for a web surface"
  - All five agents converge on the same core pattern: the model emits files inside a structured wrapper (an "artifact" / "project" envelope) using inline tags or fenced markers that carry a file path, and a client-side streaming parser turns that token stream into filesystem writes that drive a live preview, while the same file set is also exportable/downloadable as a project. The model is explicitly told, in its system prompt, what runtime surface it targets (bolt: "WebContainer, an in-browser Node.js runtime"; v0: "the 'Next.js' runtime ... runs entirely in the browser"; Lovable: "users can see a live preview ... in an iframe on the right side of the screen"), which both constrains what it can produce (no native binaries, no pip, etc.) and tells it the output is rendered, not just printed. bolt.new uses <boltArtifact>/<boltAction type="file"|"shell"|"start"> with strict action ordering (deps first, then files, then start); v0 uses <CodeProject>/<ReactProject> wrapping ```tsx file="..."``` blocks; Lovable uses one <lov-code> block containing <lov-write>/<lov-rename>/<lov-delete>/<lov-add-dependency>. Manus is the outlier: a general agent that works in a cloud "virtual computer" ("Manus's Computer" panel), writes deliverables (PPTX/PDF/CSV/XLSX/websites) into a workspace, surfaces them as downloadable artifacts plus optionally a deployed/shareable site, and offers replayable sessions. For a research/report agent the adoptable core is: define an artifact envelope, stream it into a preview pane, and present every emitted file as both previewable and downloadable.
- [10-oss-mcp-resources-and-standards.md](10-oss-mcp-resources-and-standards.md) — Standards for Agent→User Artifact/Resource Handoff: MCP, Claude Agent/Managed Agents, AG-UI, and the Vercel AI SDK
  - There is no single dominant "the agent published a file, render it for the user" standard yet; the space splits into three layers with distinct ownership. (1) MCP standardizes content-addressing: a server exposes addressable content as **resources** (URI + mimeType + text/blob), and **tool results** can either embed a resource inline (`type:"resource"`) or hand back a pointer (`type:"resource_link"`) — this is the cleanest "agent publishes a generated artifact, client renders it" primitive, and resources are explicitly "application-driven" (meant for the host UI, not just the model). (2) The agent→browser streaming layer (Vercel AI SDK 5/6, AG-UI) standardizes how typed tool outputs / data parts / file parts stream over SSE and map to rich UI components client-side. (3) Anthropic's own stack has NO first-class "artifact" type in the Claude Agent SDK (files are just `tool_result` content blocks + a `SDKFilesPersistedEvent` confirmation), but **Claude Managed Agents** does define a concrete convention: anything written to `/mnt/session/outputs/` is persisted and retrievable via the Files API with `scope_id=<session_id>`. For Scholar's claw agent, the recommendation is to model artifacts as MCP-style resources (stable URI + mimeType + audience annotation) and stream them to the SPA as Vercel-AI-SDK-shaped `file`/`data-artifact` parts, rather than inventing a bespoke envelope.
