# Scholay Wiki 建设说明

Scholay Wiki 是本仓库产品事实的可浏览知识层。它不是营销页集合，也不是把旧文档原样搬进页面；每个词条都必须能追溯到当前代码、配置、迁移或仍然有效的产品说明。

## 当前基线

- 建设分支：`scholay-wiki`
- 产品代码基线：`8b8e60689a9fd4e57309d924372f8e4dd495cfde`（`mock2`）
- 产品版本：`0.1.0`
- Wiki 入口：`/wiki`
- 内容语言：简体中文；技术标识、路由和协议名保留原文
- 当前内容：151 篇词条、730 个唯一仓库来源路径、238 个静态界面示意
- 可复现审计基线：127 个现行页面、32 个兼容跳转、57 个后端一级模块、
  7 个 Agent feature、109 个 skill、15 个小程序页面、129 个迁移、201 条冷启动工具数据

## 收录范围

“完整”按可核验的产品表面定义，至少包含：

1. Web 用户端的每条现行路由、页面与主要交互。
2. `/admin` 后台的每条现行路由、管理对象与权限边界。
3. 移动 Web 与微信小程序的每个页面和与桌面端的差异。
4. 每个用户可感知的功能、Agent 能力、工具与技能。
5. 后端每个业务域、公开/用户/管理员端点族和关键数据实体。
6. 会员、额度、钱包、支付、签到、邀请、优惠及其他活动规则。
7. 法律、隐私、帮助、反馈、内容与品牌页面。
8. 部署拓扑、运行依赖、存储、搜索、SEO 与可观测性等系统概念。
9. 已下线、迁移中或仅保留兼容性的能力；必须明确标注状态，不能与现行能力混写。

测试、生成物和纯素材不逐个写成产品词条，但必须能从“来源索引”追溯到其所属能力。研究草稿只能作为背景材料，不能单独证明现行行为。

## 事实来源优先级

出现冲突时按以下顺序裁决：

1. 当前提交中实际注册的路由、运行时代码、配置与迁移。
2. 覆盖该行为的自动化测试和契约夹具。
3. 与代码同目录且日期仍有效的说明或注释。
4. 根目录与 `docs/` 中的现行文档。
5. 研究报告、改造计划和历史 README；只用于解释背景，并标注“历史”或“待核实”。

例如根 `README.md` 仍描述已删除的独立后台与旧 React 栈，因此不能覆盖当前路由和 `CLAUDE.md` 中的事实。

## 词条模型

每篇词条至少包含：

- 稳定 slug、标题、摘要、类型和分类。
- 当前状态：现行、实验、兼容、历史或计划。
- 适用角色与入口。
- 正文中的用途、工作方式、边界/限制和相关规则。
- 至少一个当前仓库来源路径。
- 相关词条与最后核对的代码提交。

词条类型分为：

- `overview`：平台、产品矩阵和领域总览。
- `page`：一条实际产品页面或页面族。
- `feature`：跨页面能力或工作流。
- `rule`：会改变资格、额度、金额、期限、奖励或状态的规则。
- `entity`：论文、期刊、会话、订单等核心业务对象。
- `architecture`：服务、协议、存储、权限或部署概念。
- `legacy`：已下线或仅为迁移兼容保留的能力。

## 覆盖验收

最终验收不以“页面看起来很多”为准，而以覆盖清单为准：

- 每条前端现行路由必须映射到一个非空词条。
- 每个 `backend/internal/*` 业务模块必须映射到一个词条或有明确排除理由。
- 每个小程序页面、Agent feature key 和已装载 skill 必须可检索。
- 所有会影响用户权益或金额的条件分支必须落入规则词条，并引用实际实现。
- 每篇词条的来源路径必须存在；被删除或移动的来源会使校验失败。
- 不允许仅有标题的占位词条；核心章节和来源缺失即视为未覆盖。
- 构建、类型检查和 Wiki 专项覆盖检查必须通过。

## 目录

- `audit/`：按产品表面形成的代码审计底稿。
- `audit/frontend-pages-and-features.md`：初轮建设时的页面与前端功能审计底稿；现行数量以生成基线为准。
- `audit/backend-and-rules.md`：初轮建设时的后端、API 权限、业务状态机与数据实体底稿。
- `audit/agents-miniapp-infra.md`：Agent、109 个技能、15 个小程序页面、基础设施与运维边界。
- `audit/mock-component-migration.md`：初轮 product-mock 迁移底稿；现行账本为 252 个稳定可见表面、238 个 Wiki fixture 与 18 个明确排除组。
- `content-model.md`：信息架构、导航与内容字段设计。
- `scholay-wiki.xmind`：由当前 `WIKI_NAV_CATEGORIES` 同步生成的 16 栏目读者导航脑图。
- `frontend-user/src/features/wiki/`：可运行的 Wiki 页面与词条数据。
- `frontend-user/tests/wiki-content.test.ts`：词条、关联、分类与来源路径完整性检查。
- `npm run generate:wiki-baseline`：从当前路由数组、后端模块、Agent 配置/skills、小程序、迁移和冷启动工具数据生成 `coverage.ts` 基线。
- `npm run check:wiki-baseline`：只校验、不写文件；基线与扫描事实不一致时失败。
- `npm run wiki:drift -- <old>..<new>`：把 git 变更与词条 `sourcePaths`、fixture `mockSourcePaths` 求交，按词条/fixture 输出复核清单并标记过期 fixture。
- `npm run test:wiki`：内容契约与覆盖门禁；数字来自生成基线，不在测试中维护第二份手写常量，并验证 mock 可见表面全部有已注册、已挂载、带复核日期的 Wiki 组件。

## 当前核验边界

本轮对当前 checkout 做了完整静态审计和前端构建验证，但没有读取生产数据库、后台实时配置或第三方商户状态，也没有执行真实支付、退款、OAuth、微信审核、模型回合和灾难恢复演练。价格、活动、模型与外部服务的即时状态必须在目标环境再次核对；Wiki 对这些字段明确使用“仓库默认值”或“以后台实时配置为准”的口径。

## 建设纪律

- 先核对代码，再写结论。
- 数字、价格、时限和资格条件不得凭旧文档或印象填写。
- 计划中的功能必须与已上线功能分区。
- 同一事实只在一个词条中作为主定义，其他页面通过关联引用，避免多处漂移。
- 读者目录最多三级（栏目算一级）；三级以下的模式、状态和步骤归入词条正文，不再建立第四级导航。
- 产品名词只在 `content/terms.ts` 定义；正文不得使用 `deprecated` 旧称，历史引用使用精确白名单。
- 纯 mock/MSW/占位交互标为 `experimental`，只有真实后端接线足以支持词条承诺时才标为 `current`。
- 每轮更新先跑 `npm run wiki:drift -- <old>..<new>`，逐项复核命中来源和 fixture，
  再运行 `npm run generate:wiki-baseline`、`npm run generate:wiki-mcp` 与 `npm run test:wiki`。
